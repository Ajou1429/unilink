# UniLink Task Continuity

- Before each substantive task, read `docs/coaching-priorities.md` and check the current code/status relevant to the request. Briefly identify the next priority and whether the new request changes it.
- Follow the user's newest request first. Do not start unrelated roadmap work, production deployments, paid evaluations, or ongoing automatic work merely because it appears in the backlog.
- After completing a task, update the priority ledger when scope, status, dependencies, or order changed. Explain what changed and why; preserve unfinished work instead of silently dropping it.
- In the final response, briefly remind the user of remaining priorities and the immediate next step, including when the completed request was unrelated to coaching. Keep this reminder compact and avoid repeating the entire roadmap unless asked.
- Distinguish implemented, tested, committed, pushed, and deployed. Verify completion before marking an item done; prior plans and documentation are not evidence of deployment.
- Keep the ledger usable across chats and interruptions. Record blockers, dependencies, and links to implementation/evaluation documents. Do not claim account-wide memory or automatic resumption after usage limits.
