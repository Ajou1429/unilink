기준일: 2026-11-08 (KST). 로컬 코드 기준: `a354cc3`, `40fb40a`.
범위: 코드·운영 DB를 변경하지 않는 조사/설계안. 아래 후보 테이블, 필드, 평가와 학습은 아직 구현한 기능이 아니다. 운영 사용자 데이터는 조회하지 않았고 새 유료 API 평가도 수행하지 않았다.

## 1. 결론과 먼저 수정할 계획상의 전제

현재 구조를 유지하며 입력 선택·근거 연결·성과 수집을 개선할 여지가 크다. 우선순위는 관련 근거를 빠뜨리지 않는 입력, 검증 가능한 추천, 실행 결과의 추적이다. 더 강한 모델이나 긴 프롬프트만으로 해결할 문제가 아니다.

사용하면서 좋아지는 서비스는 가능하지만 다음을 분리한다.

| 개선 방식 | 바뀌는 것 | 현 시점 판단 |
| --- | --- | --- |
| DB 기반 개인 기억 | 다음 호출에 제공하는 사용자별 정보 | 먼저 도입할 대상 |
| 검토된 과거 사례 검색 | 프롬프트에 들어가는 예시 | 권한·출처 검증 후 작은 규모로 실험 |
| 시간 추정·추천 정책 보정 | UniLink의 별도 예측값·정책 | 실행 결과와 고정 연결 ID를 쌓은 후 검증 |
| LLM 파인튜닝 | 모델 파라미터 | 지원 모델·플랫폼·데이터 권리 확인 필요 |

**현재 GPT-6.1 Sol은 파인튜닝을 지원하지 않는다.** 따라서 쌓인 기록으로 운영 Sol 자체를 지속 학습시킨다고 설명하면 부정확하다. 공식 모델 페이지의 기능 표를 확인했다. [S1]

또한 OpenAI 셀프서비스 학습은 신규 접근 제한 상태다. 공식 종료 안내에 따르면 2026-05-07 신규 조직 학습 제한, 2026-07-02 최근 사용 조건 추가, 2027-01-06 기존 활성 고객의 신규 학습 작업 종료 예정이다. 계정의 학습 자격은 이번에 조회하지 않았다. 현재 Sol을 사용하며 데이터를 수집하는 것과 별도 모델을 훈련하는 일을 분리해야 한다. [S2]

Drive/Workspace API 자료에는 별도 제약이 있다. 공식 정책은 특정 사용자의 개인화 모델을 넘는 모델 생성·학습·개선을 제한하며 파생 데이터에도 적용 범위가 있다. **사용자 Drive 원문·요약·그 내용이 섞인 추천을 사용자 전체용 훈련 데이터로 자동 합치지 않는다.** 익명화나 포괄 동의만으로 허용된다고 가정하지 않는다. 개별 사용자의 개인화도 허용 사례·고지·동의·보존 조건을 확인해야 한다. 정책·저작권·개인정보 검토가 선행돼야 하며 이 문서는 법률 검토를 대체하지 않는다. [S3, S4]

## 2. 현재 구현과 확인된 개선 지점

현재는 DB-first 자료 분석/검색 캐시 → 과목별 `goal_briefs` → 최종 모델 → 서버 일정 검증 → 사용자 승인 구조다. PDF 분석 5.4-mini, 검색 4.1, 최종 Sol 분리 설정은 직전 배포 기록 기준이며 이번에는 운영 설정을 재조회하지 않았다.

| 코드 근거 | 현재 동작 | 성능상 의미 |
| --- | --- | --- |
| `functions/_shared/coaching/input.ts` | 과목별 묶음, 공통 일정, 누락/오래된 결과 표시 | 입력 연결 기반은 이미 있음. JSON→자연어 전면 전환은 불필요 |
| `functions/_shared/courseKnowledge.ts:knowledgeContext` | 개요 단원 앞 3개, 상세 단원 앞 4개, 목록 일부, 문자열을 잘라 전송 | 뒤쪽 중요 개념이 빠질 수 있음. 개별 잘림 전체가 `context_truncated`로 보고되지는 않음 |
| 같은 함수 | 과목 자료 24,000자, 검색 8,000자 예산 | 바이트/문자 예산은 토큰·의미 보존 보장이 아님. 무제한 증량 대신 선택 개선 필요 |
| `functions/_shared/coaching/context.ts` | 수업 진도 과목별 최근 10개, 학습 세션은 선택 목표 전체 최근 100개 | 활동 많은 과목이 다른 과목 이력을 밀어낼 가능성. 조회 범위 표시/목표별 균형 필요 |
| 같은 파일 | 현재 코칭 입력에 `coaching_feedback` 조회 없음 | DB에 수락 정보가 있어도 다음 추천에서 직접 활용되지 않음 |
| 같은 파일 | 세션 전달 필드에 `plan_item_id`, `method_code`, 완료 범위 등이 없음 | 어떤 추천/방법의 실행 결과인지 판단하기 어려움. DB에 있는 필드부터 연결 가능 |
| `migrations/0012_p0_planning_execution.sql` | `study_sessions.plan_item_id`, 방법, 실제 시간, 부분 완료, 전후 자기평가 존재 | 완전히 새 DB 대신 기존 관계 확장을 우선 검토 |
| `migrations/0016_coaching_runs_feedback.sql` | 버전/요청/입력 스냅샷/제안/피드백 관계 존재 | 평가와 데이터 계보의 출발점. `expires_at`만으로 실제 삭제 동작을 단정하지 말고 보존 작업 확인 |
| `migrations/0017_approve_coaching_proposals.sql` | 승인 시 accepted 피드백, `completion_criteria`는 버전만 든 기본 객체로 저장 | 완료 기준은 현재 reason 자유문장에 의존. 별도 평가/시간 보정에는 약함 |
| `functions/_shared/coaching/model.ts` | 일정과 설명을 한 번에 출력, 최소 1개 항목, Sol low/6,000 출력 상한/45초 | 모르는 경우의 안전한 응답과 실제 사고 예산을 평가할 여지. 무작정 상한 확대는 비용/시간 제한 영향 |

이는 코드상 관찰과 위험 후보이지 실제 사용자에게 모두 발생했다는 뜻은 아니다. 최근 자동 테스트·합성 API 성공도 추천의 교육적 타당성을 증명하지 않는다.

## 3. 개선 후보 전체 지도

P0는 우선 실험, P1은 데이터/국소 스키마 추가, P2는 조건부 후속 후보다. 효과 크기 수치는 측정하지 않았다.

| P2 | Bandit/RL | 정책 로그·노출 확률·보상 정의 | 축적 후 방법 선택 개선 후보 | 지금은 보류. 편향/지연 보상/안전한 탐색 문제 [S12] |
| P2 | 다중 에이전트/계획-비평 분리 | 오케스트레이션 | 복잡 과목에 역할 분리 가능 | 기본 입력 문제를 못 고침. 현재보다 복잡해지므로 명확한 실패 패턴 있을 때만 |

컨텍스트 선택은 고신호 정보를 유지하는 문제이며, 지침을 세부 알고리즘처럼 과도하게 고정하면 오히려 취약해질 수 있다. 구조와 근거 선택을 먼저 개선한다. [S6]
JSON Schema는 형식 안정성 수단이지 내용 정답 보장이 아니다. 새로운 제약은 주로 소유권·ID·시각·가용시간·자료 버전처럼 코드로 확인 가능한 사항에 둔다. [S9]

## 4. 새 입력에서 권장하는 정보

기존 입력을 버리지 않고 다음 필드를 선택적으로 추가한다. 모든 사용자가 매번 입력하는 설계는 피한다.

- 목표 결과: '3장 공부'보다 '조건을 설명하고 쿼리를 독립 작성', 목표일과 필수/선택 범위.
- 평가 형태/산출물: 시험 유형, 실습 제출물, 과제 rubric, 허용 도구, 평가 기준의 출처.
- 선수경험: 이미 배운 관련 개념, 현재 막힌 부분; 확인 시점 포함.
- 실제 진도: 수업에서 다룬 범위와 개인이 해낸 범위 분리.
- 학습 기회: 가용시간뿐 아니라 사용 가능한 기기/실습 환경, 꼭 지켜야 할 일정.
- 실행 피드백: 실제 집중시간, 완료 범위, 중단 이유, 작업이 너무 쉬웠는지/어려웠는지.
- 검증 결과: 문항 ID·개념 ID·정오·조건·시점·자료 버전. LLM이 진단한 오개념은 확정 사실이 아닌 후보.

건강·장애 같은 민감정보나 성향을 무리하게 요구/추론하지 않는다. '지금 20분밖에 없다'와 '이 사람은 항상 집중력이 낮다'를 구분한다.

## 5. DB는 기존 테이블 확장부터

아래는 제안이다. 전부 새 테이블을 만들라는 뜻이 아니다. 필드별 수집 경로, 실제 사용처와 삭제 경로가 있는 경우에만 추가한다.

| 기존 기반 / 후보 | 필요한 내용 | 먼저 할 일 |
| --- | --- | --- |
| course_knowledge_tasks / 정규화 지식 단위 | 안정 단원 ID, 원본/페이지/해시/추출 버전, 수업·주제 매핑, 근거 구분 | JSONB 아티팩트 유지; 검색/연결이 필요한 최소 단위만 투영 |
| study_plan_items | 원래 제안 항목 ID, 단원/근거 참조, 완료 기준, planned 범위 | 승인 RPC가 빈 완료 기준을 저장하는 부분부터 계약 설계 |
| study_sessions | 기존 plan_item_id·method_code 활용, completed 범위, 중단/환경 이유, 관측 시점 | 실제 UI/타이머→서버 저장→다음 입력의 전 구간 확인 |
| coaching_feedback | 항목 수준 대상, 이유 코드, 수정 전후 차이, 노출 여부/시각 | accepted 외 modified/rejected 수집을 실제 화면에서 연결 |
| learner_profiles 후보 | 검토된 사용자별 선호/시간 추정, 표본 수, 불확실성, 갱신/철회 버전 | 원본 관측과 구분. 통계 없는 단일 가중치 금지 |
| recommendation_events 후보 | run→item→노출→수정→실행 연결과 정책/입력 버전 | 기존 feedback의 부속 구조로 충분한지 먼저 검토 |
| learning_outcomes 후보 | 새 문제/지연 확인 결과, 목표 범위, 시점, 동일/유사 문제 표시 | 자기평가와 채점 결과 분리, 계획 이후 관측은 당시 입력과 분리 |
| dataset_examples / dataset_versions 후보 | 가명 ID, 입력/정답/비교쌍, 검토자, 출처/권리, 동의, split, 제외 이유, 모델/프롬프트 버전 | 서비스 원장과 학습용 데이터셋 분리 |

모든 소유 데이터의 user_id/RLS 및 복합 FK, 멱등 이벤트 키, 버전 원장과 되돌리기, 보존 기간을 설계한다. 정규화로 기존 ID를 일괄 교체하지 않는다. 마이그레이션은 additive + 구버전 기본값 + 기능 플래그 + 단계적 backfill을 기본으로 한다.

## 6. 사용 데이터로 좋아지는 실제 순서

### A. 사용 직후 개인화: 훈련 없이 가능

새 실행/피드백을 DB에 저장하고 다음 호출의 개인 프로파일/근거에 반영한다. 사용자 수정은 승인된 선호 사실로, LLM의 추론은 검토 가능한 후보로 남긴다. 사용자의 최신 수정이 오래된 프로파일보다 우선한다.

이 단계는 인컨텍스트 개인화이며 모델 파라미터 학습이 아니다. 사용자별 raw 이력을 전부 전달하지 않고 근거와 표본 수를 가진 제한 프로파일을 사용한다.

### B. 추천·시간 추정 보정

먼저 같은 활동 종류/범위/완료 기준의 예상시간 대비 실제 집중시간 오차를 검토한다. 부분 완료·타이머 방치·중단을 정상 완료와 섞지 않는다. 표본이 적으면 공통 기준 쪽에 두고, 데이터가 쌓이면 제한적으로 개인 보정을 높이는 방식이 후보지만 공식·임계값을 지금 확정하지 않는다.

실행시간 오차, 배정 적합성, 새 문제 성과, 사용자의 수정 부담을 각각 본다. 선호와 학습 효과를 단일 점수로 바로 합치지 않는다. 한 번의 자기평가 상승이나 단순한 완료 체크로 교육 효과를 학습하지 않는다.

### C. 좋은 사례를 이용한 학습 준비

한 사례는 당시 입력 snapshot + 자료 버전/근거 + 원래 제안 + 사람 검토/수정 + 실행/성과 + 데이터 사용 권리로 구성한다. 미래 성과는 정답/평가 레이블로만 쓰고 당시 입력을 재현할 때 넣지 않는다. 사용자/과목/자료 중복과 유사 문항이 train/test 양쪽에 들어가지 않게 한다.

SFT 예시는 `messages: [지침, 정제된 요청·근거, 검토된 최종 답]`, DPO 예시는 동일한 요청·제약에서 검토된 `chosen`과 `rejected` 답의 쌍이다. 지원 모델의 채팅 템플릿·데이터셋 형식에 맞게 변환한다. [S10, S11]

단, 사용자가 마감일이나 가용시간을 바꿨다면 수정 전후는 같은 입력의 선호쌍이 아니다. '수락함'도 정답 인증이 아니다. 과도하게 쉬운 계획, 허위 근거, 반복 문제, 노출되지 않은 추천, 자료 전송 실패를 정답으로 학습하지 않는다. 모델이 만든 긴 사고과정을 새로 생성·수집할 필요도 없다. 최종 판단과 검증 가능한 근거를 학습 대상으로 한다.

### D. 실제 파인튜닝 경로

Sol을 교사/기준선으로 유지하며, 학습이 허용된 별도 모델/플랫폼을 선택할 수 있다. 오픈웨이트 모델의 SFT/LoRA, 필요 시 DPO가 기술적 후보이나 라이선스·한국어/수식 성능·호스팅 비용을 별도 검증한다. 좋은 데이터를 확보했다고 작은 모델이 Sol과 같은 성능을 낸다는 보장은 없다.

처음부터 전체 코칭을 옮기기보다 자료 분류·근거 선택·작업 구조화처럼 범위가 좁은 작업부터 비교한다. 현재 지식/사용자 상태는 계속 DB에서 공급한다. 파인튜닝을 실시간 학습 상태 저장소로 쓰지 않는다.

RFT/RL이나 자동 온라인 가중치 갱신은 보류한다. 교육 성과는 늦게 나오고, 선택하지 않은 방법의 성과는 관측되지 않는다. 나중에 정책학습을 한다면 실제 노출 후보·선택·확률·결과가 필요하며 사후에 선택 확률을 꾸며낼 수 없다. [S12]

### E. 정책·권리 게이트

Drive API 원문/파생 데이터는 기본적으로 사용자 전체 훈련 풀에서 제외한다. 서비스 직접 입력도 무조건 자유롭게 학습 가능하다고 가정하지 않고, 저작권·동의·사용 목적을 검토한다. 허용된 자체 제작/공개 라이선스/권리 확보 데이터만 별도 학습 후보로 지정한다. 개인 사용자 기억과 공용 학습 데이터는 접근권한과 계보부터 나눈다. [S3, S4]

훈련 파일을 제공하면 모델 공급자에게 별도로 데이터가 전달된다. 기존 추론 동의를 학습 동의로 재사용하지 않는다. 동의 철회·삭제 요청 시 원장, 파생 프로파일, 학습 후보, 외부 학습 파일의 삭제 범위를 추적한다. 이미 학습된 모델의 개별 정보 제거는 단순 행 삭제와 다르므로 학습 전에 최소화·비식별·권리 검토가 필요하다. [S13]

## 7. 평가 설계

저장소의 단위·통합 테스트는 회귀 안전장치이고 교육 품질의 정답지는 아니다. 우선 SQL/실습 과목, 이론 과목, 개인 목표에서 일반·누락·상충·오래된 자료·과부하 사례를 모은다. 초기 30~50개는 실패 패턴 발견용 제안 규모이지 통계적 충분성이나 학습 최소량이 아니다.

| 평가층 | 질문 | 측정/검토 |
| --- | --- | --- |
| 추출 | 실제 중요한 단원/수식/과제 조건이 남았나 | 사람 표시 핵심 근거의 회수율, 페이지 일치, 수식/표 오류 |
| 조회/선택 | DB에 있는데 입력에서 빠졌나 | 원본/선택/탈락 수, 내용 위치 변화 대조 |
| 판단 | 상태가 다르면 타당하게 달라지나 | 이해도/마감/가용시간 한 항목만 바꾼 대조 평가 |
| 출력 | 과목별 구체 과업과 완료 기준인가 | 범위 일치, 근거 지지, 근거 없는 단정, 사용자 검토 |
| 일정/실행 | 계약을 지키고 실제 가능한가 | 기존 validator, 수정 부담, 완료 범위/시간, 중단 이유 |
| 비용 | 성공한 유효 추천당 비용은 얼마인가 | 분석·검색·추론·재시도·검토·DB까지 포함, p50/p95 지연 |
| 장기 결과 | 사용자가 선호하고 학습에도 도움이 되나 | 선호/이행/새 문제 성과/지연 확인을 구분, 목표 포기 감시 |

사람 검토로 기준을 만든 뒤 자동 심판을 보조로 사용한다. A/B 순서를 무작위화하고 모델명을 가린 쌍대 비교를 사용한다. 입력 형식·프롬프트·추론 강도를 동시에 바꾸지 않는다. 사용자/과목/시간 축을 분리한 holdout과 고정 회귀 세트를 운영한다. [S5, S14]

OpenAI 호스팅 Evals 제품은 공식 문서상 2026-10-31 읽기 전용 전환, 2026-11-30 종료 예정이다. 평가 자체를 하지 말라는 뜻이 아니다. 신규 평가 체계는 저장소 JSONL + 자체 실행/보고 또는 별도 평가 도구로 이동 가능하게 하고 특정 제품에 묶지 않는다. [S2]

## 8. 비용을 줄이되 성능을 희생하지 않는 원칙

- 먼저 중복/무관한 근거를 줄인다. 중요한 뒷부분을 잃는 단순 축약과 구분한다.
- 최초 PDF 분석은 정확성, 반복은 DB 재사용. 변경되지 않은 파일을 이유 없이 재분석하지 않는다.
- 텍스트/OCR/이미지는 페이지 특성에 따라 선택하며 수식·손글씨를 무조건 저해상도로 처리하지 않는다.
- 정적 지침/스키마·예시는 안정된 접두부, 동적 사용자 상태는 뒤에 두고 실제 캐시 적중률을 측정한다. Prompt caching은 DB 기억이나 학습을 대체하지 않는다. [S15]
- 어려운 사례만 medium 추론/추가 조회/비평가로 보내는 실험을 한다. 분기 기준은 실패 사례 평가로 정한다.
- 새 모델 비교는 기존 입력으로 먼저 한다. 큰 모델의 답을 자동 정답으로 삼지 않는다.
- 장시간 분석/정기 학습은 사용자 요청의 기존 동기 처리와 분리할지 후속 검토한다. 현 2분 예약·45초 시도 상한을 무작정 높이지 않는다.

## 9. 권장 실행 순서와 영향 범위

1. **P0 평가/관측**: 같은 사례 재현, 잘림 개수/선택 사유 기록, 사용자가 지적한 나쁜 계획을 익명·권리 검토된 평가 사례로 수집.
2. **P0 입력만 개선**: 중요 단원 선택, 과목별 균형, 세션 연결 필드·피드백과 관측 시점 전달. 기존 UI/출력/승인 계약 유지 가능.
3. **P1 데이터 연결**: 완료 기준·근거·실행 범위를 버전 있는 구조로 추가. 이때는 프런트/RPC/API 계약을 함께 바꿔야 하므로 별도 릴리스.
4. **사용하며 개인화**: DB 기억과 제한적인 시간 추정 보정. 사용자 수정·삭제·회귀 시 이전 버전 복귀 제공.
5. **학습 데이터셋 준비**: 출처·목적·권리 게이트, 사람 검토, split와 원본 계보를 먼저 확보.
6. **별도 모델 학습 실험**: 지원 모델/서비스가 확정된 후 SFT, 필요 시 DPO/작은 순위 모델. 성과·비용 기준선보다 좋아야 일부에만 적용.

지금 권하지 않는 것: 모든 기록을 그대로 장문 프롬프트로 전송, 엄격한 '매일 동일 분량' 규칙, 수락률만 보상으로 자동 학습, 모든 자료를 공용 훈련 데이터화, 매 요청 다중 에이전트/검색/비평가 전체 호출, 파인튜닝만 하면 RAG/DB가 필요 없다는 설계.

성공 기준과 롤백은 각 단계별로 둔다. 서비스 로직의 전체 재작성은 필요하지 않지만 새 완료 기준/ID 계약, 외부 학습 파이프라인, 읽기 도구 루프는 별도 기능 변경이라는 점을 숨기지 않는다.
