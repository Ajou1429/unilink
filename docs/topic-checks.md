# 주제별 확인 문제

## 흐름

노트 분석 → 주제 후보 확인 등록 → 수업 또는 AI 코칭의 진도·이해도 → 주제 열기 → 전송 동의 → 3문항 생성 → 답변 → 제출 → DB 채점/저장 → 다음 코칭 컨텍스트.

직접 추가한 주제는 검증된 분석 후보 연결이 없으면 생성하지 않는다. `reserve_topic_check`는 본인의 활성 목표·확정 주제·accepted 후보/target_id·완료 분석·현재 노트 버전/시각을 확인한다. 제목이나 사용자 메타데이터만으로 근거를 신뢰하지 않는다.

## 저장과 권한

- `topic_checks`: 공개 문항, 근거/자료 버전 스냅샷, 모델·프롬프트·사용량, 작업 상태. 본인 SELECT만.
- `topic_check_keys`: 정답·해설·정답 근거. 브라우저 접근 금지.
- `topic_check_attempts`: 한 check당 한 응시. 답안·정오·해설·점수·채점 버전. 점수 직접 수정 금지.
- `topic_check_states`: 주제별 최신 응시와 `source_stale`. 오류 신고로 `voided_at`이 있는 최신 결과는 코칭에서 제외하며 예전 점수로 자동 대체하지 않는다.
- `submit_topic_check`: 인증된 사용자의 응답을 서버에서 채점하고 원자적으로 저장. 같은 답 재전송은 멱등, 다른 답 재제출은 거부.
- `void_topic_check`: 문항 오류 시 본인 결과를 코칭 근거에서 제외. 이력·점수 자체는 유지.

사용자당 rolling 24시간 10회, 동시에 1개 생성. 2분 만료, 60초 모델 제한. 미응시한 동일 주제/자료 버전 문제는 재사용한다. 요청 번호 예약과 compare-and-set 생성 선점으로 HTTP 재시도에서 중복 모델 호출을 막는다. 노트 변경 시 생성 완료·새 채점을 거부한다. 원본 삭제는 문항·키·응시까지 cascade 삭제한다.

## 비용과 한계

문제 생성 입력은 저장된 노트 인용·제목·페이지 등이며 PDF 이미지 재전송이 없다. 채점은 정답 인덱스 비교라 LLM 호출이 없다. 모델은 근거 부족 시 빈 문항 배열을 반환하고 서버는 이를 실패로 표시한다. JSON 형식·인용 일치 검증만으로 정답의 의미 정확성을 보장하지 않는다.

3문항 AI 연습 점수는 자기평가와 구분한다. 전체 숙달·학습 향상·지연 기억을 증명하지 않으며 재시험은 유사 문항일 수 있다. 코칭은 오답, 마감, 사용자 상태, 시간을 함께 고려한 계획을 제안한다. 기존 승인 계획을 자동 수정하지 않는다. 서술형 평가, 문제은행 통합, 실행 기반 자동 재계획은 후속이다.

## 배포 순서

1. 대상 프로젝트 ref `lqwpcwzjbqeunqfliaso`와 마이그레이션 이력 확인. 기존 migrations가 적용된 뒤 `0025_topic_checks.sql` 적용.
2. 서버 secrets에 기존 `OPENAI_API_KEY`, `COACHING_MODEL` 유지. `TOPIC_CHECK_ENABLED=true` 설정. 선택적으로 `TOPIC_CHECK_MODEL` 지정(미지정 시 COACHING_MODEL).
3. JWT 검증을 유지해 `topic-check` 및 변경된 `coaching-propose` 배포.
4. 프런트 배포 후 실제 테스트 계정/비민감 노트로 생성·응답·채점·다음 계획의 오답 주제 반영을 확인.
5. 문항 오류 제외, 다른 사용자 차단, 노트 변경·삭제, 24시간 한도, 미설정 상태도 확인.

DB부터 배포해야 한다. 새 coaching-propose는 `topic_check_states`를 조회하므로 뷰가 없으면 503으로 실패하며 점수 누락을 숨기지 않는다. 키/모델 설정 값은 NEXT_PUBLIC 환경변수 또는 저장소에 넣지 않는다.

로컬 검증은 `npm test`, `npx tsc --noEmit`, 변경 파일 ESLint, `npm run build -- --webpack`. `tests/topic-check.test.mjs`는 실제 PGlite PostgreSQL/RLS를 사용한다. 프런트 시나리오 검증은 모의 API로 수행하며 실제 API 품질 검증과 구분한다.
