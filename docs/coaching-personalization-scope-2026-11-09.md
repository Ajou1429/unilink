# 일회성 요청과 결과 기반 개인화 분리

2026-11-10 갱신: `15d3e1c` 소스의 DB 0029/0030 및 코칭 함수 v26 운영 적용을 완료했다. 아래 미배포 설명은 11월 9일 릴리스 범위의 기록이며 최신 상태는 [운영 적용 기록](coaching-personalization-deployment-2026-11-10.md)을 우선한다. 실제 인증 API/RPC를 검증했으나 새 유료 LLM 생성의 품질 대조는 하지 않았다.

## 결정

사용자가 계획 생성 시 입력한 추가 요청은 **이번 제안에만 적용**한다. 문장에 '앞으로'가 있어도 이 경로에서 영구 선호를 자동 생성하지 않는다. 지속 개인화는 사용자가 별도로 저장한 설정, 학습 실행·진행·이해도 관측과 구조화된 만족도를 근거로 한다. 구현·검증을 완료했으며 사용자 요청으로 이번 main 커밋·푸시 범위에 포함한다. Supabase 운영 DB/서버 배포는 이번 범위에서 제외한다. 변경 영향과 후속 절차는 `coaching-personalization-release-2026-11-09.md`를 함께 따른다.

## 저장·재사용 구분

| 정보 | 현재 요청 | 지속 DB/다음 요청 |
| --- | --- | --- |
| 추가 요청, desired_outcome/constraints | 그대로 모델에 전달 | 원문을 요청 저장 필드에서 제외. 다음 요청에 자동 재사용하지 않음 |
| 과거 코칭 피드백의 자유문장 | 새 요청에 명시하면 이번에만 적용 | 다음 추천용 조회·투영에서 제외. 과거 피드백 원장은 별도 기록으로 남음 |
| 직접 저장한 선호 설정 | 현재 요청이 우선 | 기존 설정만 읽으며 추가 요청을 설정으로 자동 변환하지 않음 |
| 학습 실행·완료 범위·시간·자기평가 | 실제 기록이 있을 때 참조 | 기존 원천 기록을 근거로 활용. 없는 실제 시간을 만들어 채우지 않음 |

| 계획 만족도·난이도/시간 적합성 | 선택적으로 기록 | 한 계획당 현재 평가 한 개, 수정·삭제 가능. 학습 효과/특정 주제 숙달로 취급하지 않음 |
| 생성된 계획·설명과 승인 결과 | 사용자 검토 | 별도 코칭 결과로 보존. 일회성 요청 내용이 결과에 반영될 수 있으나 장기 선호로 재해석하지 않음 |

## 코드 반영

- `coachingRequestPayload`는 목표 ID·요청 종류·기간과 중복 방지용 요청 해시만 저장한다. `one_off_text_present`는 문장이 있었는지 여부일 뿐 원문을 복원하지 못한다. 동일 키의 다른 요청 거절과 승인 RPC의 기간·시간대 경로는 유지한다. 원문이 없으므로 과거 요청 전체를 정확히 재현하는 기능은 제한된다.
- 마이그레이션 `0030_scoped_personalization.sql`은 기존 `coaching_runs.request_payload`도 같은 최소 필드로 정리하고, 트리거로 이후 쓰기를 제한한다. 원문 필드 제거는 되돌릴 수 없으므로 운영 적용 전에 대상·보존 정책 확인과 정상적인 백업/승인 절차가 필요하다. 백업이나 외부 로그까지 이 SQL이 정리하는 것은 아니다.
- 요청 텍스트는 브라우저 React 상태에만 두고 생성 성공 또는 창 닫기 후 비운다. 생성 실패 시 수정·재시도를 위해 현재 입력을 유지한다. localStorage에는 저장하지 않는다.
- 과거 `coaching_feedback.explanation`은 모델 입력에서 제외한다. 수락/거절은 해당 제안의 결정 기록이지 만족도나 영구 선호의 증거가 아니다.
- 새 `coaching_satisfaction`과 저장/삭제 RPC는 본인의 생성 완료 제안에만 접근할 수 있다. 같은 계획을 반복 평가해도 관측 수가 늘지 않는다. 점수 1~5와 난이도/배정 시간 적합성만 저장하며 새 자유문장 칸은 없다.
- `coaching_satisfaction_evidence`는 목표·계획·시점 및 일회성 요청 존재 여부를 제공한다. 일회성 요구가 있던 계획의 높은 만족도를 미래의 같은 요구에 대한 지지로 해석하지 않는다.
- `learner_personalization_events`는 기존 학습 실행·이해도 및 새 만족도를 모은 사용자별 DB 뷰다. LLM이 쓴 성격 프로파일 테이블이 아니다. '내 개인화 근거 기록'에서 선택 목표의 최근 30개를 확인한다. 이 화면은 모든 입력/평생 이력을 보여주는 것은 아니다.
- 입력 v5/지침 v16은 반복되고 비교 가능한 원천 관측으로 잠정 조정하도록 한다. 단 한 번의 만족도나 부분 완료로 학습 속도·집중력·영구 성향을 확정하지 않으며, 모델 파라미터 학습이나 자동 가중치 학습을 했다고 말하지 않는다.
- 근거 화면은 과목 변경 중 이전 과목의 기록을 섞어 표시하지 않고, 실제 시간이 비어 있으면 0분이 아니라 미기록으로 표시한다.

## 보존 경계와 적용 주의

- 새 만족도를 삭제하면 앞으로의 만족도 조회와 근거 뷰에서 제외된다. 이전 코칭 입력 스냅샷·생성 결과까지 함께 삭제하는 기능은 아니다.
- 기존 과목 메모·명시적인 이해도 기록·문제은행·승인된 계획은 삭제하지 않는다. 이미 일회성 요구를 반영해 생성된 계획을 임의 재작성하지 않는다.
- 기존 API의 `store:false`와 독립 요청 구조를 유지한다. 이는 서비스의 DB 정책 및 공급자 측 로그/보존 정책과 별개이며 '어디에도 데이터가 전혀 남지 않는다'는 보장이 아니다. [OpenAI 대화 상태 안내](https://developers.openai.com/api/docs/guides/conversation-state)
- 모델 종류·일정 검증·승인 계약·PDF/검색 캐시를 바꾸지 않았다. 유료 모델 성능 비교는 이번 작업에서 하지 않았다.
- 별도의 LLM 호출이나 프로파일 생성은 추가하지 않았다. 다만 과목별 최근 만족도/이해도 조회와 입력 근거가 늘어 DB 조회 시간과 입력 토큰은 증가할 수 있다. 각각 과목별 최근 20개로 제한하고 최신 이해도와 같은 관측 ID는 중복 전달하지 않는다. 비용 절감이나 추천 성능 향상 수치는 아직 측정하지 않았다.
- 운영 전체 적용 권장 순서: 앞선 0029 확인 → 0030의 원문 제거 범위 검토/DB 적용 → `coaching-propose` 배포 → 프런트 배포 → 실제 계정 통합 확인. 단, 이 저장소는 main 푸시로 웹 화면이 먼저 자동 배포될 수 있다. DB 미적용 시 새 만족도 UI는 적용 대기로 표시한다. 화면 배포만으로 서버의 원문 비저장·이력 전달 정책까지 바뀌지 않는다. 개인정보 안내도 이 중간 상태를 명시하며, 실제 통합 적용 후 문구를 다시 확정한다.

## 검증

- 자동 테스트: 원문이 현재 모델 요청에는 있으나 저장용 payload에는 없음, 요청 해시 구분, 이전 자유문장 미전달, 최신/과거 이해도 ID 중복 방지, 만족도 소유권·범위·점수 검증·중복 방지·수정·삭제·다음 입력 연결.
- PostgreSQL 호환 시험 DB에서 마이그레이션, 트리거의 원문 제거와 중복 방지 해시 보존, RLS 및 원천 근거 뷰를 검증했다. 운영 DB나 실제 사용자 데이터를 수정하지 않았다.
- Node 132개·Edge 10개, 프런트/서버 타입 검사, 린트 및 최종 정적 빌드 통과. OneDrive의 빌드 임시 파일 읽기 전용 속성으로 첫 빌드가 막혔으나 해당 임시 출력 속성만 바로잡은 뒤 정상 완료했다.
- 가상 API를 사용하는 Playwright로 PC 1365px/모바일 390px에서 첫 요청만 원문 전송, 다음 요청 빈 값, 창 닫기/다시 열기 후 입력 비움, localStorage 원문 없음, 만족도 저장·삭제와 근거 조회, 미기록 시간을 0분으로 표시하지 않음, 실행 오류·만족도 패널 넘침 없음 확인.
