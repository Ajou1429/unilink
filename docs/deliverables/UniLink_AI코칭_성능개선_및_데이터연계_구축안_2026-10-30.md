# UniLink AI 코칭 성능 개선 및 데이터 연계 구축안

작성일: 2026-10-30
문서 목적: 과목 지식 DB 기반 코칭의 구현과 운영 반영 결과를 정리하고, 실제 사용 검증부터 실행 피드백과 개인별 추천 보정까지의 다음 작업을 정의한다.
검토 기준: main 구현 커밋 b975965, 운영 Supabase lqwpcwzjbqeunqfliaso, 마이그레이션 0025부터 0027까지. 10월 28일과 29일 개정본의 성능 우선 및 데이터 기반 보정 방향을 통합했다.
문서 상태: 운영 DB와 관련 함수, 사이트 배포 및 기능 활성화 확인 완료. 실제 강의자료를 이용한 교육적 품질 평가는 후속 작업이다.

핵심 결론은 자료를 이해하는 코칭의 기반을 먼저 확보하고, 그 결과를 사용자의 실제 학습 수행과 연결해 개인별 시간 추정과 추천 방식을 보정한다는 것이다. 이번에는 과목 자료를 최초에 분석해 DB에 저장하고, 이후에는 저장된 지식과 최신 학습 상태를 이용하는 흐름을 구현했다. 일반적인 공부 계획을 만드는 LLM 호출만 추가한 단계와 구분된다. 다만 구현과 배포가 완료됐다는 사실이 추천의 교육적 효과까지 검증됐다는 의미는 아니다.

## 2. 코칭이 해결해야 하는 문제

개선 전에는 하루 120분과 3일 같은 시간 정보만으로 개념 학습, 문제풀이, 모의고사를 기계적으로 나열하는 문제가 있었다. 좋은 코칭은 다음 질문에 근거를 가지고 답해야 한다.

1. 해당 과목이나 개인 학습에서 실제로 무엇을 배우고 어느 깊이까지 수행해야 하는가?
2. 사용자는 어디까지 배웠으며 어떤 개념을 이해하거나 어려워하는가?
3. 강의 예제와 과제, 시험, 선수지식 중 무엇이 우선인가?
4. 실제 빈 시간 안에서 어떤 자료로 어떤 활동을 얼마나 수행해야 하는가?
5. 실행 후 확인한 시간과 이해도 차이를 다음 추천에 어떻게 반영할 것인가?

LLM은 내용 해석과 수준 판단, 학습 작업 구성과 설명을 담당한다. UniLink 하네스는 자료 근거와 Learner State, 일정, 출력 검증, 승인 및 실행 이력을 연결한다. 하네스가 교육적 판단을 임의의 고정 가중치 하나로 대체해서는 안 된다.

## 3. 현재 구현된 데이터 흐름

### 3.1 최초 계획 요청

1. 사용자의 진도와 일정 변경 사항을 기존 P0 동기화로 DB에 저장한다.
2. 선택한 수업 또는 개인 목표에 명시적으로 연결된 PDF를 찾는다. 다른 수업의 유사한 제목만으로 자료를 합치지 않는다.
3. PDF 전송 동의를 확인한다. 원본 바이트 해시와 페이지 수를 확인하고 Drive 변경 시각이 맞지 않으면 동기화부터 요구한다.
4. 모든 PDF의 전체 페이지를 최대 10쪽씩 구조 분석한다. 강의계획서, 강의, 실습, 과제, 시험, 참고 자료가 혼합된 경우 구간별로 나눈다.
5. 실제 수업 진도와 연결된 범위 중 상세 분석이 없는 부분을 최대 6쪽씩 추가 분석한다.
6. 검색이 활성화되고 사용자가 별도로 동의한 경우 실제 추출 개념과 요구 깊이를 기준으로 외부 자료를 검색한다.
7. 분석 결과와 원본 PDF, 페이지, 해시, 버전, 모델, 프롬프트, 사용량 및 검색 근거를 DB에 저장한다.
8. 저장된 과목 지식과 사용자 상태, 일정으로 구체적인 학습 작업을 제안한다. 사용자가 승인해야 실행 계획에 저장한다.

### 3.2 같은 진도에서 재추천

같은 PDF와 같은 진도에서는 원본 다운로드나 PDF 분석, 외부 검색을 다시 실행하지 않는다. DB의 지식과 최신 학습 상태를 조회하고 계획 생성 모델만 호출한다. 사용자가 이해도나 실제 공부시간만 바꾸면 자료 지식의 캐시 키는 바뀌지 않는다. DB 결과를 재사용한다는 의미이지, 계획 생성 LLM 호출까지 없어졌다는 뜻은 아니다.

### 3.3 새 수업 진도 반영

파일이 바뀌지 않아도 새 진도에 상세 근거가 필요한지 확인한다. 3쪽부터 5쪽까지 이미 분석했고 실제 수업이 7쪽까지 진행됐다면 6쪽부터 7쪽만 추가 분석한다. 앞부분과 강의계획서 전체를 다시 보내지 않는다. 새 상세 분석에서 기존에 없던 개념이 나타난 경우에만 추가 검색 후보가 생긴다.

노트 ID 또는 고유한 노트 제목과 페이지 범위를 우선 사용한다. 페이지가 없으면 유일하게 일치하는 단원이나 개념이 있는 경우에만 연결한다. 모호한 경우 자료 범위 확인 필요로 남기며 업로드 시각이나 현재 날짜로 수업 진도를 추정하지 않는다.

### 3.4 자료 변경과 명시적 재분석

신규 PDF는 신규 자료만, 수정 PDF는 변경된 자료만 분석한다. 노트 메타데이터만 바뀌면 원본 인덱스를 다시 확인할 수 있지만 바이트 해시가 같으면 비싼 모델 분석은 재사용한다. 검색 캐시는 개념 순서와 대소문자 차이 때문에 불필요하게 다시 생성하지 않도록 정규화한다.

사용자가 특정 PDF의 재분석을 요청하면 새 분석 세대를 만들고 이전 결과를 보존한다. 다른 PDF와 여전히 유효한 검색 근거는 유지한다. 재분석 이후 노트 제목만 바뀌어도 이전의 오래된 분석 세대로 되돌아가지 않는다.

| 구분 | 저장하는 내용 | 사실과 추정의 구분 |
| --- | --- | --- |
| 강의계획서 | 개요, 목표, 학점, 선수지식, 주차별 교육과정, 평가, 과제와 시험 안내, 교재 | 실제 문구와 페이지를 연결. 모호한 날짜는 원문대로 유지 |
| 강의와 실습 자료 | 단원, 개념, 공식, 예제, 문제 유형, 실습, 목표, 선수 관계 | 원본에서 확인한 내용과 근거 인용을 저장 |
| 요구 깊이와 방법 | 설명, 계산, 증명, 구현 등 요구되는 수행과 공부 방식 | 자료 과업을 해석한 AI 판단이며 검증된 성취 점수가 아님 |
| 외부 참고 분석 | 개념별 깊이, 선수지식, 학습법, 이론과 실습 등의 난이도 추정 | 실제 강의 범위를 대체하지 않는 보조 근거 |
| 학습시간 | 단원 자율학습 시간 범위와 판단 근거 | 타 학생의 실측 평균이나 개인에게 확정된 소요시간이 아님 |
| 추적 정보 | 자료 ID, 페이지, 버전, 해시, 분석 세대, 모델과 프롬프트, 사용량 | 어떤 근거를 어떤 조건에서 읽었는지 재현하는 기록 |

강의계획서의 예정 진도, 자료가 제공된 범위, 실제 수업 진행, 상세 분석 완료, 사용자 학습 완료, 충분한 이해는 각각 다른 상태다. 자료가 올라왔다고 수업이 진행됐다고 판단하지 않고, 공부를 완료했다고 이해도가 상승했다고 판단하지 않는다.

코칭에는 현재 진도에 필요한 상세 근거를 우선 전달하고 강의계획서와 관련 구조, 검색 결과를 제한된 길이로 포함한다. 모든 과목의 모든 분석 JSON을 매번 넣지 않는다. 일부만 선별된 경우 범위 제한을 표시한다. 현재 방식은 구조화된 DB 근거 선별이며 전체 원문 임베딩 검색이 완성된 것은 아니다.

## 5. Learner State와 기존 DB의 연결

| 기존 데이터 | 현재 코칭에서 사용하는 정보 | 남은 보완 |
| --- | --- | --- |
| learning_goals와 courses | 과목 및 개인 목표, 중요도, 목표일, 수업 연결 | 목표 성적과 선수 경험을 정규 입력으로 확장 |
| course_sessions | 선택 과목별 최근 10회 진도, 제목, 메모, 체감 난이도와 속도, 노트 및 페이지 | 메타데이터 필드를 정규화하고 누적 진도 조회 보완 |
| topic_observations | 주제별 자기평가, 상태, 시점, 메모, 노트와 회차 | 자기평가 편향과 정정 이력, 관측 부족 표시 보완 |
| topic_check_states | 주제별 최신 확인 결과와 시점, 출처, 자료 변경 여부 | 소수 문항을 전체 숙달로 해석하지 않기 |
| calendar_events | 과제와 시험, 마감, 범위, 고정 일정 | 자료의 모호한 날짜는 자동 확정하지 않음 |
| study_plan_items | 기존 계획과 계획 시간, 일정, 상태 | 지식 단원의 고정 ID와 과업을 연결 |
| study_sessions | 실제시간, 완료 상태, 이전과 이후 평정 | 중단과 부분 완료, 미완료 이유, 완료 범위 정규화 |
| coaching_runs와 feedback | 요청과 당시 컨텍스트, 제안, 승인과 피드백 | 노출, 수정 전후 차이, 과업별 성과 연결 |

데이터가 DB에 있다는 것과 필요한 정보가 모델에 전달된다는 것은 다르다. 저장, 조회, 프롬프트 반영, 결과의 근거 사용을 각각 확인해야 한다. 입력 누락이나 동기화 실패를 무시한 채 최신 상태라고 설명하지 않는다. 자기평가, 문제 점수, 공부시간, 내용 난이도와 사용자 부족 정도도 분리한다.

개인 목표도 자료와 확인 주제, 학습 기록을 사용한다. 현재 수업 회차를 기준으로 한 자동 상세 범위 갱신은 실제 수업 기록에 연결된다. 회차가 없는 개인 목표의 세부 과업 범위를 별도로 기록하고 조회하는 구조는 이후 더 보완한다.

## 6. 외부 검색의 역할과 제한

검색은 과목명만으로 일반 정보를 찾는 방식이 아니다. PDF에서 실제 추출한 개념과 요구 깊이를 입력으로 사용하고 대학 교육과정과 신뢰할 수 있는 교육 자료를 우선 참고한다. SQL JOIN이라도 정의 설명만 필요한지 결과 예측과 쿼리 작성까지 필요한지 실제 강의자료와 비교해야 한다.

실제 완료된 검색 도구 호출이 있어야 성공으로 표시한다. 검색 출처 또는 인용 메타데이터에 없는 URL은 저장을 거절한다. 출처 URL과 제목, 확인 일자, 관련성, 신뢰도 설명, 근거와 불확실성을 보존한다. 화면에는 클릭 가능한 출처가 표시된다.

외부의 고급 내용을 실제 수업의 필수 범위로 추가해서는 안 된다. 학습시간을 뒷받침할 근거가 부족하면 범위를 비워두고 이유를 표시한다. 검색 실패나 미설정, 동의 거절은 PDF와 DB 근거만 사용하는 제한 상태다. 실제 검색을 한 것처럼 표현하지 않는다.

검색 입력에는 추출된 주제와 개념, 요구 수준을 사용한다. 원본 PDF 전체, 계정 정보, 사용자 이해도와 학습 이력은 검색 요청에 넣지 않는다. 개념 자체가 비공개 정보일 수 있으므로 PDF 전송 동의와 검색 동의를 분리했다. 검색 단계당 도구 호출은 최대 2회이며 과금은 별도로 발생할 수 있다.

출처가 실제로 검색됐다는 사실이 해당 설명의 교육적 정확성을 보장하지는 않는다. 공식 자료 여부와 실제 수업 관련성, 인용의 의미 일치는 대표 사례에서 사람이 확인해야 한다.

운영 합성 검증에서 gpt-4.1-mini 검색 응답의 출처 메타데이터가 부족하거나 JSON의 URL과 불일치하는 사례가 확인됐다. 검색 전용 모델을 gpt-4.1로 분리하고, 먼저 검색 보고서와 실제 출처를 받은 뒤 그 URL만 enum으로 허용하는 구조화 평가를 수행하도록 보완했다. 최초 연구 단계에는 두 모델 호출이 발생할 수 있다. 구조화 평가만 실패하면 저장된 검색 보고서를 재사용하며, 정상 완료한 연구 결과는 이후 계획에서 다시 검색하지 않는다.

## 7. 주제 확인 문제의 현재 구현

1. 사용자가 기존 노트 분석 후보를 확인해 수업 또는 개인 목표의 주제로 등록한다.
2. 해당 주제를 열고 저장된 근거의 전송에 동의한 뒤 객관식 3문항을 생성한다.
3. 모델에는 노트 제목, 근거 인용, 페이지와 버전을 보내며 PDF 이미지를 다시 보내지 않는다.
4. 서버는 문항 수, 보기, 정답 범위, 중복과 근거 문자열을 검증한다. 근거가 부족하면 실패로 표시한다.
5. 사용자가 전 문항에 답하면 DB 함수가 정답키와 비교해 정오와 해설, 점수와 버전을 원자적으로 저장한다.
6. 다음 코칭에 점수와 자료 버전, 관측 시점을 자기평가와 구분해 전달한다.

정답키는 topic_check_keys에 두고 브라우저의 조회를 차단한다. 동일 답안 재전송은 멱등이며 제출 후 답안을 바꾸는 재제출은 거절한다. 자료가 바뀌면 새 답안 채점과 생성 완료를 차단하고 기존 결과는 과거 근거로 표시한다. 오류 문항은 사용자가 코칭 반영에서 제외할 수 있다.

이 기능은 LLM이 문제를 생성하고 서버가 객관식 정오를 채점하는 방식이다. 서술형 평가나 풀이 과정 분석, 교육자가 검토한 시험과는 다르다. 3문항 전부 정답이어도 전체 숙달이나 장기 기억을 확정하지 않는다. 새 과목 지식의 모든 단원에서 즉시 확인 문제를 만드는 통합도 아직 별도 작업이다.

## 8. 시간 추정과 개인 맞춤 추천의 기준

과목 자체의 요구 수준과 사용자에게 필요한 학습량을 분리한다. 같은 자료라도 선수 경험이 부족한 사용자는 개념과 기초 실습이 필요하고, 충분히 이해한 사용자는 새 과제나 취약한 적용 문제에 집중할 수 있어야 한다.

현재는 자료와 외부 참고의 추정 시간 범위, 자기평가, 확인 결과, 실제 학습 이력과 마감, 가용시간을 모델이 종합하도록 연결했다. 추정 근거가 없으면 진단 활동이나 임시 배분으로 표시한다. 일반적인 모든 과목에 개념, 문제, 모의고사를 동일하게 배치하지 않도록 지시한다.

분 단위 배정은 실행을 위한 제안이지 검증된 필요시간의 확정값이 아니다. 단 한 번의 공부시간이나 완료 체크로 학습 속도를 확정하지 않는다. 정규 수업 시간과 자율학습 시간을 구분하고, 여러 과목의 합계가 가용시간을 넘으면 부족분과 우선순위를 설명해야 한다.

시간창, 고정 일정, 수업, 이동과 휴식, 하루 학습 예산은 서버가 검증한다. 기존 계획을 임의로 삭제하거나 완료 상태를 되돌리지 않는다. 현재 실행 계획 API의 1일부터 14일까지 계약을 유지한다. 강의계획서의 주차별 교육과정은 학기 참고 자료로 조회되지만 학기 전체를 자동 달력 배치하는 스케줄러는 아직 아니다.

## 10. DB와 서버 설정의 운영 기준

course_knowledge_tasks는 작업 체크포인트와 구조화된 지식 아티팩트를 겸한다. index, overview, detail, research, refresh를 구분한다. 사용자와 목표, 노트의 소유권 FK, 결정적 작업 키, 원본 해시와 범위, 분석 세대, 결과와 사용량을 기록한다. 성공 결과는 보존하고 실패 단계만 재시도한다.

사용자당 동시에 한 단계만 허용한다. 24시간 보수적 60단계, 단계당 최대 3회, 임대 150초와 외부 요청 115초 제한을 둔다. 만료된 작업은 재개할 수 있고 늦게 끝난 작업은 새 임대를 덮어쓸 수 없다. 공개 직전 노트 버전과 수정 시각을 같은 DB 트랜잭션에서 검증한다.

coaching_service_settings는 API 키가 아닌 기능 활성화와 선택 모델만 저장한다. knowledge_enabled, research_enabled, topic_check_enabled, analysis_model, research_model을 관리한다. anon과 authenticated에는 읽기와 쓰기를 모두 허용하지 않는다. service role 및 운영 DB 관리자만 관리하며, 명시적인 환경변수가 우선한다.

PDF는 기존 20MB와 50쪽 제한을 따른다. 목표당 노트 조회 40개, 수업 기록 100개, 지식 아티팩트 1500개 상한을 초과하면 조용히 일부만 처리하지 않고 범위 조정을 요구한다. 실제 초기 자료량을 보고 제한과 처리 시간을 조정하되 비용 검증 없이 일괄 해제하지 않는다.

한 요청이 한 단계를 예약하고 백그라운드 작업으로 처리한다. 화면은 상태를 확인하고 다음 단계를 이어간다. 창을 닫으면 진행 중 단계까지만 끝날 수 있으므로 다시 열어 분석 이어가기를 누른다. 별도 상시 워커가 배포된 것은 아니다.

## 11. 바뀐 화면의 사용 순서

1. AI 코칭에서 계획을 세울 목표를 선택한다. 선택 박스와 목표 이름이 같은 행에 표시된다.
2. 수업 진도, 노트와 페이지 범위, 자기평가를 확인하고 저장한다.
3. 과목 지식에서 자료 분석 상태와 강의계획서 인식, 상세 진도 및 검색 상태를 확인한다.
4. 새 분석이 필요하면 PDF 전송에 동의한다. 외부 검색은 별도로 선택한다.
5. 계획 생성을 요청한다. 중단됐다면 분석 이어가기를 누르고, 특정 PDF가 잘못 해석됐다면 그 PDF만 재분석한다.
6. 내용과 학습 근거에서 실제 진도, PDF 페이지, 요구 수준과 공부 방법, 시간 추정과 출처를 확인한다.
7. 제안의 구체 작업과 시간 배치를 검토하고 승인한 뒤 실행 계획으로 저장한다.

자료가 없거나 범위가 모호한 상태는 제한 추천으로 구분한다. 분석이 실패한 사실을 숨기지 않는다. 외부 검색을 선택하지 않아도 이미 준비된 PDF와 DB 근거로 추천할 수 있다. 같은 상태의 DB 재사용에 매번 새로운 PDF 전송 동의를 요구하지 않는다.

## 12. 이번 검증과 아직 입증하지 않은 것

Node 자동 테스트 115개, Deno Edge 테스트 9개, 전체 Edge 타입 검사, 프런트 TypeScript, 전체 ESLint 경고 0, Webpack 정적 빌드와 19개 페이지 생성이 통과했다. 1365px과 390px에서 새 분석 화면과 기존 확인 문제 흐름을 모의 API로 검증하고 화면을 확인했다.

실제 Edge 처리 코드와 PostgreSQL을 함께 실행한 통합 검증에서 최초 분석, 같은 상태 재사용, 3쪽부터 5쪽만 전송하는 새 진도 분석, 최종 코칭 모델 입력의 상세 개념 사용을 확인했다. 검색 URL, 페이지 범위, 임대 선점과 만료, 소유권, 비공개 정답키, 재분석 세대, 환경변수 우선순위도 검사했다.

운영 DB에서는 브라우저의 지식 작업 INSERT, 정답키 SELECT 및 서버 설정 SELECT가 차단됐음을 확인했다. 적용 전후 수업 22개, 노트 226개, 목표 23개, 계획 항목 34개, 학습 세션 0개로 집계가 동일했다. 0025부터 0027까지의 적용 이력과 새 테이블 5개의 RLS 활성화를 확인했다.

실제 배포 URL의 데스크톱과 모바일 번들에서도 분석 화면, 동의, 출처 링크, 재추천의 캐시 재사용을 모의 API로 검증했다. 운영 함수 4개의 비로그인 호출은 모두 401로 차단됐다.

추가로 개인정보가 없는 1쪽 SQL JOIN 합성 PDF와 임시 테스트 계정으로 실제 운영 API를 검증했다. PDF 분석 1단계, 외부 연구 1건에서 실제 출처 3개 저장, 같은 상태 재요청의 분석 작업 추가 0개, 코칭 제안 2개 생성을 확인했다. 실제 코칭 모델은 gpt-4.1-mini였고 검색은 gpt-4.1로 동작했다. 테스트 계정과 PDF, 그 계정에 속한 결과는 종료 후 정리했으며 기존 사용자 자료는 읽거나 모델에 전송하지 않았다.

이 검증은 구조와 보안, 캐시 및 실제 API 연계를 확인하는 것이다. 합성 자료에서 동작했다는 사실이 실제 강의 노트의 의미 해석, 문항 타당성, 개인별 시간 추정, 성적이나 이해도 향상을 입증하지는 않는다. 실제 과목 자료를 이용한 품질 평가는 후속으로 진행한다.

| P0 | 실제 과목 2개 이상과 개인 목표 1개의 대표 자료로 처음부터 끝까지 사용 | 자료 분류와 핵심 개념, 요구 깊이, 근거 페이지가 실제 자료와 맞음 |
| P0 | 같은 상태에서 다시 계획 생성 | PDF와 검색 재실행 없이 계획 생성만 호출. 재사용 근거가 오래되지 않음 |
| P0 | 실제 진도를 다음 구간으로 변경 | 부족한 페이지에만 상세 분석이 발생하고 다음 계획에 새 내용이 반영 |
| P0 | 이해도만 낮추거나 높여 비교 | 자료 지식을 다시 만들지 않고 작업과 복습 비중이 근거에 맞게 달라짐 |
| P0 | 마감과 가용시간만 바꿔 비교 | 충돌과 과부하 없이 분량과 우선순위가 달라지고 부족분을 설명 |
| P0 | 검색 근거와 문항을 사람 검토 | 실제 수업에 없는 고급 범위, 가짜 근거와 모호한 정답이 없음 |
| P1 | 예상과 실제시간, 완료 범위, 중단과 미완료 이유 수집 | 계획 항목과 실행 결과를 안정적 ID로 연결 |
| P1 | 추천 품질 기준선과 사용량 측정 | 내용 정확성, 구체성, 시간 제약, 불확실성, 비용을 함께 비교 |

기본 성능이 나아졌는지는 같은 사례에서 이전 추천과 새 추천을 비교해 판단한다. 전체 토큰을 늘리거나 호출 수가 많아졌다는 이유만으로 성능 향상이라고 설명하지 않는다. 검토 사례와 평가 사례는 분리하고 유사한 문항과 같은 자료가 양쪽에 과도하게 겹치지 않게 한다.

## 14. 다음 개발 단계 실행 결과에 따른 재계획

현재는 이해도와 확인 결과가 다음 계획 생성에 들어간다. 기존 계획을 자동으로 바꾸거나 변경 차이를 비교하는 재계획 전체가 완성된 것은 아니다. 다음 단계에서는 기존 study_plan_items, study_sessions, coaching_runs, coaching_feedback를 재사용한다.

1. 계획 항목별 실제시간, 완료 범위, 미완료 이유와 외부 일정 변화를 기록한다.
2. 해당 항목이 어떤 지식 단원과 추천 버전에서 생성됐는지 고정 ID로 연결한다.
3. 마감과 남은 학습량, 취약 주제와 가용시간으로 변경 계획 후보를 만든다.
4. 기존 계획과 변경된 범위, 시간, 이월 이유를 미리 보여준다.
5. 사용자가 승인한 변경만 반영하고 완료 항목, 직접 수정한 내용과 원래 실행 이력을 보존한다.
6. 이월 중복과 동시에 수정하는 다른 기기, 오래된 제안의 승인을 검증한다.

저장이 부족한 항목은 추천 노출 및 수정 이력, 과업 단위 성과, 미완료 사유, 단원 연결, 보정 버전이다. 기존 테이블의 확장으로 충분한지 먼저 확인하고, 필요할 때 recommendation_events, learning_outcomes, recommendation_policy_versions 또는 동등한 구조를 추가한다. 후보 테이블이 이미 구현됐다고 문서에 표시하지 않는다.

## 15. 사용 데이터 기반 보정의 순서

추천 노출, 수락, 수정과 거절, 실제 수행, 학습 결과를 초기 사용자 테스트부터 모은다. 다만 먼저 자료 기반 코칭의 기본 품질을 확보하고 그다음 보정을 적용한다. 잘못된 자료 해석을 사용자 가중치로 덮어서는 안 된다.

| 보정 대상 | 필요한 관측 | 잘못된 해석 방지 |
| --- | --- | --- |
| 개인 필요시간 | 비교 가능한 과업의 예상과 실제시간, 완료 범위와 기준 | 중단과 부분 완료, 타이머 방치를 정상 완료시간으로 취급하지 않음 |
| 학습 방법 적합성 | 이전 상태, 수행 방법, 새 문제나 설명의 결과, 지연 후 확인 | 선택과 만족도만으로 학습 효과를 확정하지 않음 |
| 우선순위 | 마감, 취약점, 선수지식, 복습 지연, 사용자의 수정 이유 | 쉬운 과목만 선택되거나 일부 목표가 계속 방치되지 않게 점검 |
| 하루 분량과 블록 길이 | 수행량, 중단과 피로, 일정 변화, 실제 결과 | 시간이 없었던 경우를 내용 난이도 실패로 오인하지 않음 |
| 복습 시점 | 마지막 학습과 평가 시점, 이후 새 관측 | 관측이 없다는 이유만으로 망각을 확정하지 않음 |

첫 보정 대상으로 개인별 필요시간 추정을 권장한다. 같은 과업 범위와 완료 기준의 기록을 비교하고 실제시간 대비 예상시간의 차이 같은 단순한 보정부터 검증한다. 표본이 적으면 공통 기준을 유지하고, 관측이 쌓이면 개인 보정 비중을 높인다. 한 번의 극단적인 결과로 추정이 급격히 바뀌지 않게 한다. 구체적인 공식과 임계값은 아직 확정하지 않는다.

처음에는 새 추정치를 실제 추천에 적용하지 않고 과거 기록에서 오차와 추천 차이를 검토한다. 시간 순서와 사용자 및 과목 구분을 고려해 별도 평가 자료로 검증하고 미래 성과를 과거 입력에 넣지 않는다. 이후 적용 범위를 제한해 기존 방식과 비교하며 악화되면 이전 버전으로 되돌릴 수 있게 한다.

수락률과 클릭률 하나만 최적화하지 않는다. 시간 추정 오차와 실행 가능성, 학습 성과, 수정 부담과 목표 방치 여부를 함께 본다. 특정 방법의 효과를 주장하려면 사용자 상태와 난이도 차이를 통제한 비교가 필요하다. 유사 사용자 분석은 데이터와 평가가 충분해진 뒤 진행한다.

이는 LLM 자체 가중치를 바꾸는 파인튜닝과 다르다. 초기에는 UniLink의 근거 선택, 사용자 상태, 필요시간 추정과 추천 정책을 개선한다. 파인튜닝은 좋은 자료와 입력이 있는데도 행동과 형식 문제가 반복되고, 검토된 학습 사례와 평가셋이 확보된 다음 별도로 검토한다.

## 16. 아직 남은 기능과 혼동하면 안 되는 범위

- 학기 전체 실행 일정 자동 배치. 현재는 주차별 교육과정 참고와 1일부터 14일까지 실행 제안이다.
- 개인 학습의 세부 과업 범위를 수업 회차 없이 정규 기록하는 구조.
- 지식 단원과 기존 확정 주제, 계획 항목, 실행 결과의 고정 ID 통합.
- 새 지식 단원의 충분한 원문을 활용하는 확인 문제 생성과 서술형 및 적용 평가.
- 전체 원문의 페이지별 텍스트 저장과 임베딩 검색, 선택적 OCR, 수정 페이지 해시 비교.
- 계획 변경 차이 미리보기와 부분 승인, 안전한 미완료 이월.
- 개인 시간 추정과 방법 적합성의 통계적 보정, 유사 사용자 기반 초기 추천.
- 실제 추천 품질과 비용을 지속 비교하는 평가셋 및 운영 대시보드.

이 항목들을 API 키만 넣으면 자동으로 생기는 기능으로 설명하지 않는다. 현재 구축한 자료 지식과 상태 연계는 이 기능들이 가능해지는 기반이며, 각각 구현과 검증이 필요하다.

## 17. 운영 장애 확인과 롤백

원본 Drive 수정 시각이 다르면 먼저 Drive 변경 반영을 실행한다. 노트와 페이지 연결이 모호하면 실제 진도를 정정한다. 실패한 단계는 성공 결과를 보존한 상태에서 재시도한다. 3회 실패했다면 원인을 해결한 뒤 해당 PDF의 새 분석 세대를 요청한다. 검색만 실패하면 그 사실을 표시하고 PDF 및 DB 기준으로 진행할 수 있다.

서비스 전체 문제가 있으면 새 테이블이나 기존 학습 기록을 삭제하지 않는다. 서버 전용 설정의 knowledge_enabled 또는 research_enabled를 false로 전환하고 프런트 기능 플래그와 함께 맞춘다. 명시적 환경변수에 값이 있으면 DB 설정만으로 바뀌지 않으므로 운영 관리자에게 확인한다. 모델이나 API 키는 별도 권한을 가진 관리자가 변경한다.

기존 서버 함수 소스를 되돌릴 때도 DB 데이터를 DROP하지 않는다. 제안 이력과 승인, 완료 기록을 보존하며 사용자 자료의 재전송이나 원본 삭제를 자동 실행하지 않는다. 비밀값이나 인증 코드를 문제 보고나 문서에 포함하지 않는다.

## 18. 팀에서 확인할 의사결정

1. 초기 품질 평가를 맡을 대표 과목과 실제 강의자료, 개인 목표를 정한다.
2. 사람이 자료 분류와 요구 수준, 인용 의미, 확인 문제 정답을 검토할 담당자를 정한다.
3. 현재 운영 모델을 기준선으로 유지하고 다른 모델과 비교할 때 같은 입력 및 평가 기준을 사용한다.
4. 공개 사용 전 사용자별 초기 분석량과 검색 허용, 비용 상한과 재시도 안내를 확인한다.
5. 실제시간과 완료 범위를 입력하는 부담을 줄이면서 계획 항목과 연결되는 UX를 정한다.
6. 추천 수정과 거절, 미완료 이유를 선택 항목과 자유 입력으로 어떻게 수집할지 정한다.
7. 교수님 테스트 계정의 Drive 권한과 테스트 자료를 준비하고 개인정보가 있는 자료는 별도로 주의한다.

## 19. 교수님과 팀에 설명할 현재 단계

UniLink는 기존 학습 기록과 플래너 DB를 기반으로 학습 계획을 제안하는 LLM 코칭 에이전트를 구축했고, 과목별 PDF 자료를 분석해 지식 DB로 저장하고 이후 계획에 재사용하는 기반까지 추가했다. 실제 수업 진도의 부족한 범위만 증분 분석하고, 자기평가와 확인 문제 결과, 가용시간과 마감을 함께 반영하도록 연결했다. 생성 계획은 사용자가 승인해야 반영된다.

앞으로 실제 과목 자료로 기본 추천 품질을 평가하고, 계획별 수행 시간과 완료 범위, 이해도 변화를 축적할 예정이다. 이 데이터로 개인별 시간 추정과 학습 방법 및 우선순위를 보정하고, 검증된 반복 판단은 수식과 알고리즘으로 옮겨 비용과 일관성을 개선한다. 현재부터 학습된 개인화 모델이나 검증된 교육 효과를 보유했다고 주장하지는 않는다.
