## 실행 플랜

### 1차: 현재 추천 품질과 누락 입력 확인 - 1~3번

1. SQL/실습, 이론, 개인 학습의 같은 요청에서 자료·진도·기한·가용시간을 고정한다. 이해도 미입력/낮음/높음만 변경한 비교 세트를 준비한다. 자기평가와 채점이 충돌하거나 오래된 경우도 별도 사례로 둔다.
2. 먼저 무료 자동 테스트로 실제 모델 요청의 값과 소유권·출처·시점 보존을 검증한다. 유료 생성 비교는 호출 수와 비용 범위를 정한 별도 실행으로 진행하고 여러 번 반복해 우연한 출력 차이를 구분한다.
3. 낮은 이해도는 적절한 선수 개념 보완·작은 적용으로, 높은 이해도는 불필요한 재학습 감소·새 응용으로 연결되는지 검토한다. 이해도가 낮으면 무조건 시간을 늘리거나 높으면 무조건 시간을 줄이라는 규칙으로 만들지 않는다. 범위와 가용시간을 함께 조절해야 한다.
4. 실제 자료의 목표·선수지식·과제 요구와 DB 추출 및 최종 선택 근거를 대조한다. 이미 있는 분석/검색을 새 기능으로 재구축하지 않는다. 발견한 누락·잘못된 수준 판단을 기준으로 입력 선택이나 지침만 국소 보완한다.
5. 문제은행의 과목→학습 목표 및 문제→주제 연결을 설계하고 해당 level의 의미를 함께 전달한다. 다른 척도를 산술 평균하지 않는다. 연결/입력이 없어도 기존 자료와 주제 이해도로 추천할 수 있어야 한다.

완료 산출물: 대조 평가 사례와 결과표, 입력 누락/근거 오류 목록 및 수정, 문제은행 연결의 소유권·척도·범위 검증. 입력이 전달된다는 사실과 추천이 좋아진다는 결과를 분리해 보고한다.

### 2차: 개인 기록이 실제로 쌓이는 흐름 - 4~5번

1. 기존 study_plan_items.completion_criteria에 작업 범위·검증 가능한 완료 기준·근거 참조를 채우는 계약부터 정한다. 출력 스키마→서버 검증→승인 RPC→DB→화면을 함께 맞추고 과거 계획은 그대로 읽을 수 있게 한다.
2. 항목별 완료/부분 완료, 실제 공부시간, 해낸 범위, 미완료 사유를 적은 조작으로 기록하게 한다. 자기 이해도 수정 및 계획 수정/거절 이유는 선택 기록으로 받는다.
3. 원래 추천 항목→실행 관측→다음 모델 요청을 끝까지 검증한다. 자동 측정하지 않은 시간을 실측으로 만들거나 완료 체크를 숙달로 간주하지 않는다. 새 기록은 개인 소유권·중복 방지·수정 이력을 갖춘다.

완료 산출물: 승인된 완료 기준, 실제 사용 가능한 기록 UI와 저장 경로, 다음 추천에서 같은 관측 ID가 반영되는 통합 테스트.

### 3차: 실행 결과 기반 조정 - 6~7번

1. 이해도 변화·완료 범위·미완료 사유와 남은 기간으로 새 계획을 제안한다. 단순 날짜 이동이 아니라 범위 축소/선수 개념/복습·응용 선택을 상황에 맞게 조절한다.
2. 기존 계획과 바뀌는 내용을 미리 보여주고 승인 후 반영한다. 원래 계획과 관측을 덮어 지우지 않는다.
3. 비교 가능한 개인 기록이 쌓인 후 활동별 시간 추정 오차를 검토하고 개인 배정을 보정한다. 표본 수·범위·관측 시점·불확실성과 복귀 방법을 남긴다. 선호·계획 이행·새 문제 성과는 따로 평가한다.

완료 산출물: 변경 계획 미리보기·승인 흐름, 근거 있는 개인별 추정과 비교 결과. 모델 파인튜닝이나 사용자 전체 데이터 학습은 이번 범위가 아니다.

### 병행: 비용 관리 및 릴리스 확인

- 원문 PDF는 변경/필요 구간이 생겼을 때만 기존 분석 정책에 따라 처리하고 저장된 분석을 재사용한다.
- 최근 run 전체 스냅샷 대신 필요한 연결 정보만 조회하는 방안, 무관한 이력/빈 필드/반복 지침 축소를 검토한다. 근거 의미와 소유권을 보존한 뒤 비교한다.
- 각 단계마다 구체성·수준 적합성·근거·일정 준수와 토큰·재시도·응답시간을 함께 기록한다. 현재 총 토큰 증가를 비용 절감으로 포장하지 않는다.
- 기존 자동 테스트·타입 검사와 합의한 품질 사례에서 회귀가 없는지 확인한 뒤 단계별 커밋/릴리스한다. 실제 운영 배포와 DB 변경은 요청·권한 범위에서 별도 진행한다.

### 이해도 입력 확인 결과

- 주제별 자기 이해도: `TopicLearningPanel` → `record_topic_observation` → `topic_observations` → 최신 상태 `topic_learning_states` → `modelContext` → `goal_briefs[].self_reports`. 상태·자기평가 1~5·메모·시점·노트/페이지를 전달한다.
- AI 확인 문제: `topic_check_states`의 정답 수/문항 수와 자료 버전 등을 `goal_briefs[].scored_checks`로 별도 전달한다. 이를 자기 이해도 점수로 자동 환산하거나 단일 가중 점수로 합치지 않는다.
- 문제은행 이해도: 이전에는 코칭에 미연결이었다. 이번 로컬 구현에서 `problem_bank_coaching_links`→`coaching_problem_bank_states`→`goal_briefs[].problem_bank_stages` 경로를 추가했다. 명시적으로 연결한 문제은행만 읽고, 주제 자기 이해도 1~5와 다른 단계 척도로 전달한다. 운영 DB/서버에는 아직 미적용이다.
- 따라서 기존 ‘문항별 오답 연결’ 우선 설명은 정정한다. 주제 이해도 입력이 없는 상태가 아니라, 이미 있는 이해도와 별도 기록의 연결·활용 품질을 확인하는 것이 우선이다. 이 확인은 로컬 main 코드 기준이며 운영 배포/실제 계정 데이터 상태는 별도 확인 사항이다.

- 현재 명시적 요청이 과거 선호보다 우선한다. 일정·시간·권한·승인은 강제 조건으로 유지한다.
- 모든 과목에 같은 개념/문제/모의고사 순서나 시간 비율을 강제하지 않는다.
- 이해도만·마감만·시간만 바꾸는 대조 사례와 여러 과목의 반복 평가를 늘린다. 수락·완료를 학습 효과로 간주하지 않는다.
- 과목별 구체성, 근거 정확성, 실행 가능성, 사용자 수정 부담, 새 문제 성과, 비용을 구분해 평가한다.

## 변경 이력

커밋 전 영향 검토 결정: 문제은행 조회 오류는 누락된 근거로 추천하지 않는 중단 방식을 유지한다. 연결 화면과 개인정보 안내에 AI 전송 범위·연결 해제 후 이전 기록 보존을 명시했다. 실제 운영 DB·서버 적용과 계정 통합 확인은 남아 있다. 영향 상세는 `coaching-phase1-2026-11-09.md`를 따른다. 다음 기능 개발은 4번이며 운영 릴리스 조건 확인은 별도로 선행한다.

- 2026-11-09: 사용자의 요청에 따라 매 작업 전후 우선순위 확인·상기 및 변경 이유 기록 방식을 도입했다. 기능 개발이나 운영 배포를 새로 수행한 것은 아니다.
- 2026-11-09: 사용자 지적 후 이해도 입력 경로를 재확인했다. 주제 이해도와 채점 결과의 별도 전달을 확인하고 문항별 오답 상세는 선택 고도화로 내렸다. 문제은행 level 미연결을 우선 확인 대상으로 명시했다. 서비스 코드는 변경하지 않았다.
- 2026-11-09: 수정된 이해도 입력 사실을 기준으로 실행 플랜을 재정리했다. 현재 입력의 효과 검증→과목 요구 수준/근거 보완→문제은행 연결을 1차로 두고, 완료 기준/실행 수집 및 재계획/개인 보정을 후속 단계로 분리했다. 비용 관리는 병행하며 문항별 오답 상세는 후순위로 유지한다. 이번 변경은 계획 문서만 갱신한 것이다.
- 2026-11-09: 사용자 요청으로 1~3번을 로컬 구현·검증했다. 입력 v4/지침 v15, 합성 이해도 대조 실제 호출 12회, 자료 근거 선택 보완, 문제은행 연결 UI/0029/코칭 전달을 추가했다. 운영 DB/서버 배포 및 커밋·푸시는 하지 않았다. 실제 PDF 대조와 복잡도 조절은 열린 후속이며 다음 기능 개발은 4번이다.
- 2026-11-09: 사용자 요청으로 영향 검토 및 AI 전송 안내 보완을 포함해 커밋·푸시를 진행한다. 문제은행 장애 시 중단 동작은 유지하고 운영 DB·코칭 서버 배포는 제외한다. 실제 완료 커밋은 Git 이력과 최종 작업 보고를 따른다.
- 2026-11-09: 사용자 요청으로 개인화 기억 범위를 먼저 분리했다. 일회성 원문 비저장/미재사용, 만족도와 이해도 이력의 구조화된 근거, 사용자 근거 확인을 로컬 구현했다. 0030은 기존 요청 원문 필드를 제거하므로 운영 적용 전 범위 확인이 필요하다. 커밋·운영 적용은 별도이며 기존 4번 및 나머지 5~7번을 유지한다.
- 2026-11-09: 사용자 요청으로 개인화 범위 분리의 main 커밋·푸시와 변경 영향 정리를 진행한다. Node 132개·Edge 10개·타입·린트·정적 빌드 및 PC/모바일 가상 API 검증을 통과했다. 웹 자동 배포만으로 DB/서버의 새 정책이 적용되지 않으므로 이 상태를 안내에 반영했다. Supabase 운영 적용 및 실제 계정 확인은 남기고 기존 4번을 다음 기능 개발로 유지한다.
