## 2026-11-17 통합 비서 1차 로컬 구현·검증

사용자가 구축 시작을 승인했다. 아래의 '구축 전/문서만' 항목은 이전 검토 이력이다. 채팅과 시스템 전체를 연결하는 작업으로 범위를 확정하되, 모든 서비스 도구의 구현 완료를 뜻하지 않는다.

로컬 구현: `service-agent` 서버의 두 경로 분류·제한된 읽기/작업 준비 도구, 독립 Terra 모델 설정, 새 통합 동의·기능 플래그, 기존 관측 기록/파일 처리 연결, 승인형 신규 일정과 시간표 DB 조회, 기존 코칭 입력 미리 채우기·선행 기록/일정 게이트. 파일 단독은 비서 자료 처리만 수행하며, 텍스트+파일은 등록 의도를 먼저 확인한다. 일회성 텍스트는 영구 개인화에 저장하지 않는다. 세부 범위와 운영 전 조건은 [통합 비서 1차 구현 기록](service-agent-release-2026-11-17.md)을 따른다.

검증: 전체 자동 테스트 250개, 타입·린트·서버 함수 타입·프로덕션 빌드 통과. 통합 ON/OFF 모두 PC/모바일 채팅·코칭 흐름 확인. 신규 통합 테스트는 모델/DB HTTP를 대체한 시험이므로 실제 모델 품질 검증은 남았다. 운영 활성화 전이며 모든 서비스 기능의 자연어 처리가 완성된 상태는 아니다.

다음 우선순위: **운영 웹/DB/함수 계약 대조 → 서버 배포·제한 공개 및 실제 Terra 분류/비용 평가 → 서버 소유 작업/승인 원장과 재개·경합 검증 → 수정·삭제·반복 일정·자료 지정/근거 설명·채팅 코칭 보완**. 현재 일정 쓰기는 기존 본인 JWT/RLS 경로의 추가 저장만 지원하며 서버 승인 원장/RPC를 구현한 것으로 표시하지 않는다. 새 migration·운영 배포·커밋/푸시는 하지 않았다. 기존 Drive 원본 대조·코칭 품질 평가·실행 기록·승인형 재계획·개인 보정 작업은 유지한다.

자료 단독 입력 규칙: 코칭 요청 없이 파일만 첨부하면 비서로 처리해 자료 종류·과목·중복/버전 확인과 허용된 등록만 수행한다. 업로드를 계획 생성·이해도·학습 완료로 해석하지 않는다. 유효한 기존 코칭의 자료 대기 상태만 요청 ID에 연결해 계속할 수 있다. 구축안·평가 예시에 반영했으며 코드·PDF·운영은 변경하지 않았다. 다음 분류/작업 계약과 평가셋 작성 우선순위는 유지한다.

2026-11-17 후속 검토: 기존 코칭 모델·성능/추천 경로를 우선 유지하고 서비스 비서는 `gpt-6.1-terra`, 초기 분류기도 같은 모델에 분리된 지침/출력 계약을 적용하는 안으로 정리한다. 기존 구조도 PDF에 기술·흐름·모델·실행 책임을 덮어써 사용자 확인을 받는 단계이며 **구축은 아직 시작하지 않는다**. 모델의 실제 계정 접근·품질 평가도 미실시다. 검토 후 아래 분류/도구 계약부터 진행하며 나머지 미완성 작업은 유지한다.

## 2026-11-16 서비스 비서와 코칭 분류기 설계

사용자 최신 요청으로 기존 코칭을 재구축하지 않고 통합 채팅의 상위 경로를 **코칭 / 비서 두 가지**로 정리했다. [서비스 비서·분류기 구축안](service-assistant-architecture.md)에 현재 코드 차이, 구조도, 분류 예시, 복합 요청 알고리즘, 도구/승인/DB 계약, 비용과 검증 순서를 남겼다. 이 문서는 향후 구현 계획이며 임시 산출물이 아니다.

후속 요청으로 작업 폴더의 `UniLink_통합AI에이전트_구조도_2026-11-16.pdf`를 같은 이름의 A3 가로 한 페이지 에이전트 구조도로 덮어썼다. 분류기·비서 확장·기존 코칭 재사용·혼합 요청 순서·공통 실행/승인·공유 DB를 표시하고 렌더링을 확인했다. 기능 구현이나 배포 상태는 바뀌지 않았으며 아래 우선순위를 유지한다.

새 학습 내용·깊이·시간·우선순위 판단은 코칭, 조회/기록/일정/파일/기존 계획 조작과 그 외 요청은 비서로 접수한다. 혼합 요청은 세 번째 경로 대신 필요한 비서 작업을 확인·저장한 뒤 최신 상태로 코칭한다. 비서 접수가 무조건 쓰기를 뜻하지 않으며 미지원/모호 요청은 질문·안내로 종료한다. 일회성 맥락과 명시 기록 요청을 분리하고 기존 원문 비저장·자기보고/채점 구분을 유지한다.

상태: 로컬 main `d69e948`과 첨부 PDF·공식 기술 문서를 검토하고 **문서만 변경**했다. 분류기/비서 기능 코드·DB migration·실제 모델 평가·커밋/푸시·운영 배포는 미실시다. 현재 코칭의 필수 목표/시간창/시험 입력을 자연어와 본인 DB에서 연결할 어댑터 및 자유 진단 요청의 별도 계약이 필요하다. 브라우저 저장/서버 쓰기 중복과 outbox·다기기 충돌도 선행 검증한다.

다음 새 기능 개발 순서는 **실제 채팅/운영 계약 대조 → 분류/도구/승인 계약·평가셋 → 공통 진입점과 조회/학습 기록 → 일정·자료 비서 → 코칭 어댑터/혼합 요청 → 실제 사용 평가**다. 기존 Drive 원본/전체 동기화 확인, 실제 코칭 품질 비교, 실행 기록 UI·승인형 재계획·개인 DB 보정 작업은 삭제하지 않고 유지한다. 운영 migration 번호는 이전 원격 전용 이력과 대조한 뒤 결정한다.

1~3번의 코드와 이번 개인화 변경은 운영 배포 및 기본 검증을 마쳤다. 사용자 본인의 새 생성/추천 내용 확인은 별도로 남아 있다. 다음 구현은 H0-A의 승인 안전 경계와 실행 계약을 작은 변경으로 먼저 검증하고, 사용자 기능은 4번 완료 기준 구조화를 진행한다. H0-B/C의 최소판은 4번과 함께 준비하되 대규모 하네스 재설계를 이유로 4~7번을 무기한 미루지 않는다. 실제 자료 대조와 낮은 이해도의 과제 부담·상충 관측 검토는 1~2번의 후속으로 유지하고 비용 관리는 병행한다.

## 실행 플랜

### 선행·병행: 하네스의 실행 안전과 개선 기반 - H0

1. H0-A 첫 단위: 만료/생성 후 일정 변경/서로 다른 run 동시 승인/수동 수정과 승인 경합의 재현 시험을 만든다. 단순 run 잠금이나 UI의 승인 클릭만으로 최신 정합성이 보장된다고 설명하지 않는다.
2. 일회성 원문을 제외한 시간창·규칙·시간대·근거/일정 버전의 실행 계약을 설계한다. 현재 최소 request payload에 없는 정보를 재현할 수 있다고 가정하지 않는다. 새 계약 저장·이전 v2 읽기·승인 시 최신 재검증·공통 쓰기 직렬화를 함께 구현한다.
3. H0-B/C 최소판: 기존 run/job/usage 및 평가 스크립트를 재사용하고 단계·허용 오류·버전·제한된 근거 참조만 연결한다. 전체 원문/비밀키/모델의 숨은 추론을 로그나 외부 tracing 서비스에 복사하지 않는다.
4. 개인 추천 개선과 서비스 개선을 분리한다. 본인 실행/이해도/평가는 다음 추천의 근거이고, 프롬프트·도구·모델/규칙 변경은 팀의 재현→대조→승인→단계적 배포를 거친다. 운영 AI가 자기 지침을 무승인으로 수정하지 않는다.
5. 공개 확대 전 환경 분리·복구·비용/동시 실행·장애 지원·권한/동의·실제 pilot 기준을 확인한다. 현 main/dev Pages 경로와 별도 Supabase 배포의 정합성을 출시 manifest로 관리하는 계획을 세운다. 새 인프라/유료 평가/운영 변경은 별도 요청 범위에서 수행한다.

완료 산출물: 승인 회귀 시험과 실행 계약, 한 요청의 원문 없는 단계 기록, 대표 평가셋/비교 기준, 배포·복구 체크리스트. 자세한 책임·DB 재사용·검증 기준은 `database/coaching-harness.md`를 따른다. 이번에는 해당 기능을 구현한 것이 아니라 계획을 정립했다.

### 1차: 현재 추천 품질과 누락 입력 확인 - 1~3번

2026-11-11부터 R1/R2 내용 계약을 함께 검토한다. 먼저 과목 요구 수준과 선수 기반/현재 진도/이해 확인의 구분, 일회성 텍스트와 시험/복습 필요의 조정, 하루·주간·시험의 검토 범위를 합성 사례로 확인한다. 그 뒤 자료 없는 검색·문제은행 본문/필요 역량·선수 관련 이력을 필요한 경로부터 연결한다. 사용자의 명시 제외나 실행 목표를 몰래 늘리지 않는다. 현재 검색/조회가 새 경로를 이미 지원한다고 가정하지 않는다.

1. SQL/실습, 이론, 개인 학습의 같은 요청에서 자료·진도·기한·가용시간을 고정한다. 이해도 미입력/낮음/높음만 변경한 비교 세트를 준비한다. 자기평가와 채점이 충돌하거나 오래된 경우도 별도 사례로 둔다.
2. 먼저 무료 자동 테스트로 실제 모델 요청의 값과 소유권·출처·시점 보존을 검증한다. 유료 생성 비교는 호출 수와 비용 범위를 정한 별도 실행으로 진행하고 여러 번 반복해 우연한 출력 차이를 구분한다.
3. 낮은 이해도는 적절한 선수 개념 보완·작은 적용으로, 높은 이해도는 불필요한 재학습 감소·새 응용으로 연결되는지 검토한다. 이해도가 낮으면 무조건 시간을 늘리거나 높으면 무조건 시간을 줄이라는 규칙으로 만들지 않는다. 범위와 가용시간을 함께 조절해야 한다.
4. 실제 자료의 목표·선수지식·과제 요구와 DB 추출 및 최종 선택 근거를 대조한다. 이미 있는 분석/검색을 새 기능으로 재구축하지 않는다. 발견한 누락·잘못된 수준 판단을 기준으로 입력 선택이나 지침만 국소 보완한다.
5. 문제은행의 과목→학습 목표 및 문제→주제 연결을 설계하고 해당 level의 의미를 함께 전달한다. 다른 척도를 산술 평균하지 않는다. 연결/입력이 없어도 기존 자료와 주제 이해도로 추천할 수 있어야 한다.

완료 산출물: 대조 평가 사례와 결과표, 입력 누락/근거 오류 목록 및 수정, 문제은행 연결의 소유권·척도·범위 검증. 입력이 전달된다는 사실과 추천이 좋아진다는 결과를 분리해 보고한다.

### 2차: 개인 기록이 실제로 쌓이는 흐름 - 4~5번

1. 기존 study_plan_items.completion_criteria에 작업 범위·검증 가능한 완료 기준·근거 참조를 채우는 계약부터 정한다. 출력 스키마→서버 검증→승인 RPC→DB→화면을 함께 맞추고 과거 계획은 그대로 읽을 수 있게 한다.
2. 항목별 완료/부분 완료, 실제 공부시간, 해낸 범위, 미완료 사유를 적은 조작으로 기록하게 한다. 자기 이해도 수정 및 계획 수정/거절 이유는 선택 기록으로 받는다.
3. 원래 추천 항목→실행 관측→다음 모델 요청을 끝까지 검증한다. 자동 측정하지 않은 시간을 실측으로 만들거나 완료 체크를 숙달로 간주하지 않는다. 새 기록은 개인 소유권·중복 방지·수정 이력을 갖춘다.

완료 산출물: 승인된 완료 기준, 실제 사용 가능한 기록 UI와 저장 경로, 다음 추천에서 같은 관측 ID가 반영되는 통합 테스트.

### 3차: 실행 결과 기반 조정 - 6~7번

1. 이해도 변화·완료 범위·미완료 사유와 남은 기간으로 새 계획을 제안한다. 단순 날짜 이동이 아니라 범위 축소/선수 개념/복습·응용 선택을 상황에 맞게 조절한다.
2. 기존 계획과 바뀌는 내용을 미리 보여주고 승인 후 반영한다. 원래 계획과 관측을 덮어 지우지 않는다.
3. 비교 가능한 개인 기록이 쌓인 후 활동별 시간 추정 오차를 검토하고 개인 배정을 보정한다. 표본 수·범위·관측 시점·불확실성과 복귀 방법을 남긴다. 선호·계획 이행·새 문제 성과는 따로 평가한다.

완료 산출물: 변경 계획 미리보기·승인 흐름, 근거 있는 개인별 추정과 비교 결과. 모델 파인튜닝이나 사용자 전체 데이터 학습은 이번 범위가 아니다.

### 병행: 비용 관리 및 릴리스 확인

- 원문 PDF는 변경/필요 구간이 생겼을 때만 기존 분석 정책에 따라 처리하고 저장된 분석을 재사용한다.
- 최근 run 전체 스냅샷 대신 필요한 연결 정보만 조회하는 방안, 무관한 이력/빈 필드/반복 지침 축소를 검토한다. 근거 의미와 소유권을 보존한 뒤 비교한다.
- 각 단계마다 구체성·수준 적합성·근거·일정 준수와 토큰·재시도·응답시간을 함께 기록한다. 현재 총 토큰 증가를 비용 절감으로 포장하지 않는다.
- 기존 자동 테스트·타입 검사와 합의한 품질 사례에서 회귀가 없는지 확인한 뒤 단계별 커밋/릴리스한다. 실제 운영 배포와 DB 변경은 요청·권한 범위에서 별도 진행한다.

### 이해도 입력 확인 결과

- 주제별 자기 이해도: `TopicLearningPanel` → `record_topic_observation` → `topic_observations` → 최신 상태 `topic_learning_states` → `modelContext` → `goal_briefs[].self_reports`. 상태·자기평가 1~5·메모·시점·노트/페이지를 전달한다.
- AI 확인 문제: `topic_check_states`의 정답 수/문항 수와 자료 버전 등을 `goal_briefs[].scored_checks`로 별도 전달한다. 이를 자기 이해도 점수로 자동 환산하거나 단일 가중 점수로 합치지 않는다.
- 문제은행 이해도: 이전에는 코칭에 미연결이었다. `problem_bank_coaching_links`→`coaching_problem_bank_states`→`goal_briefs[].problem_bank_stages` 경로를 추가하고 2026-11-10 운영 DB/서버에도 반영했다. 명시적으로 연결한 문제은행만 읽고, 주제 자기 이해도 1~5와 다른 단계 척도로 전달한다. 현재 실제 연결이 없으므로 근거가 이미 들어온다고 가정하지 않는다.
- 따라서 기존 ‘문항별 오답 연결’ 우선 설명은 정정한다. 주제 이해도 입력이 없는 상태가 아니라, 이미 있는 이해도와 별도 기록의 연결·활용 품질을 확인하는 것이 우선이다. 이 확인은 로컬 main 코드 기준이며 운영 배포/실제 계정 데이터 상태는 별도 확인 사항이다.

## 공통 판단 기준

- 실제 자료 사실 / 생성 연습 / 외부 추정 / 사용자 자기평가 / 채점 결과를 구분한다.
- 강의 수준, 수업에서 다룬 진도, 개인 수행 범위와 숙달을 별도로 기록한다.
- 현재 명시적 요청이 과거 선호보다 우선한다. 일정·시간·권한·승인은 강제 조건으로 유지한다.
- 위 '요청 우선'은 과거의 소프트 선호에 대한 원칙이지 임박한 시험/과제나 필요한 재확인을 무시하라는 뜻이 아니다. 요청의 내용·어려움을 중요하게 반영하고 놓친 후보/대안을 제안하되 명시 제외·가용시간·선택 범위는 사용자 선택 없이 변경하지 않는다.
- 일반 요구 수준은 자료/검색으로, 개인 선수 기반·이해도는 본인 관측으로 판단한다. 과제/강의 예제의 시험 역량 연결은 근거를 표시하고 별도 제출 기준과 마감을 보존한다. 어려운 내용의 반복 확인도 최근 확인 범위/시점·남은 기간·사용자 부담을 보고 유연하게 제안한다.
- 모든 과목에 같은 개념/문제/모의고사 순서나 시간 비율을 강제하지 않는다.
- 이해도만·마감만·시간만 바꾸는 대조 사례와 여러 과목의 반복 평가를 늘린다. 수락·완료를 학습 효과로 간주하지 않는다.
- 과목별 구체성, 근거 정확성, 실행 가능성, 사용자 수정 부담, 새 문제 성과, 비용을 구분해 평가한다.
