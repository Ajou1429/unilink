# UniLink 서비스 시뮬레이션 DB

검증일: 2026-09-29. 작업 브랜치: `DB-ver`.

## 목적과 격리

가상 사용자와 사용 시나리오를 생성하고, **실제 마이그레이션·RLS·FK·프런트 저장 모듈·Edge Function 코드**를 실행한다.
DB는 PGlite의 로컬 PostgreSQL이며, `.simulation/`에 영구 저장된다. 운영 Supabase를 수정하거나 실제 Google/Gemini 요청을 보내지 않는다.
현재 웹사이트에 이 DB를 연결한 것은 아니다. 생성 계정은 가상 세션을 사용하며, 실제 Supabase 로그인 계정이나 비밀번호가 없다.
테스트 통과를 운영 환경 전체 기능 검증으로 해석하면 안 된다.

## 실행

PowerShell에서 저장소 루트를 기준으로 실행한다.

```powershell
# 매번 새로운 난수값, 사용자 12명, 별도 DB 디렉터리 생성
npm.cmd run simulate:db

# 동일한 사용자/시간표 조합 재생성. 사용자 수는 2~50명.
npm.cmd run simulate:db -- --seed 20260929 --users 12

# 가장 최근에 생성한 DB를 다시 열어 실제 저장 건수와 검사 결과 조회
npm.cmd run simulate:inspect

# 기존 회귀 검사 + 사용자 3명의 인메모리 시뮬레이션
npm.cmd test
```

동일 seed는 사용자·시간표 조합을 재현한다. DB 자동 UUID와 실행 시각까지 바이트 단위로 동일하지는 않다.
시나리오 날짜는 `2026-09-29`, 학기는 `2026-2`로 고정하여 재현 가능성을 유지한다.
매 실행은 새 디렉터리를 만들며 이전 결과를 삭제하거나 기존 DB를 초기화하지 않는다.
테스트 실패는 보고서에 기록되고 명령은 종료 코드 1을 반환한다.

## 결과 파일

`.simulation/latest.json`이 가장 최근 실행 디렉터리를 가리킨다.

| 파일 | 내용 |
| --- | --- |
| `run-<seed>-<timestamp>/db/` | 재사용 가능한 로컬 PostgreSQL 데이터 디렉터리 |
| `report.md`, `report.json` | 시나리오 결과, 데이터 수, 검증 범위와 제외 항목 |
| `users.json` | 가상 사용자 ID·이메일·유형·과목 수 |
| `sample-lecture.pdf` | 실제 PDF 파서로 열 수 있는 문제 예제 파일 |
| `files/`, `files.json` | 모의 Storage 파일 원본과 객체 경로 대응표 |

DB 내부 `simulation.results`에 검사 결과, `simulation.run_config`에 생성 조건을 보관한다.
`simulation.browser_snapshots`는 브라우저 전용 기능의 검사용 스냅샷이다. 이 테이블은 **운영 마이그레이션이나 해당 기능의 서버 저장 구현이 아니다.**
생성 결과는 Git에서 제외한다. 가상 인증 정보는 실사용할 수 없으며 운영 프로젝트로 가져오면 안 된다.

## 데이터와 검사 범위

| 범위 | 검사 내용 | 실행 방식 |
| --- | --- | --- |
| 사용자 격리 | 다른 사용자 조회·변경 차단, 소유권 FK, 비밀 컬럼 접근 제한 | 실제 PostgreSQL 역할·RLS |
| 시간표 | 여러 요일·주말·이른 시간, 요일별 다른 시간, 수정 후 복원 | 실제 저장 모듈 → SQL |
| 기타/월간 일정 | 반복 일정·하루 일정·목표 기한, 삭제 후 재등장 방지 | 실제 저장 모듈 → SQL |
| 강의 진도 | 진도 제목·메모·페이지·난이도 보존 및 변경 후 복원 | 실제 저장 모듈 → SQL |
| 계획·실행 | 과목/주간/월간 미러 중복 방지, 개인 계획, 완료·부분완료·중단 실행 | 실제 저장 모듈·SQL |
| 문제은행 | 과목·문제 저장, 수준 0~5, 삭제, 다른 사용자 접근 제한 | 실제 저장 모듈 → SQL |
| PDF 문제 추출 | 실제 PDF 파싱, 추출 결과 저장·중복 방지, 잘못된 파일/응답과 실패 작업 정리 | 실제 Edge 코드, **Gemini 응답은 모의** |
| 자료·노트 | 실제 PDF 파일 업로드 경로·권한, 과목/개인학습 분류 | 실제 저장 모듈, Storage 전송은 모의 |
| Drive 인증 | PKCE·재사용 차단·잘못된 검증값/다른 계정 거부·암호화·만료·재연결·해제 | 실제 Edge 코드, **Google 응답은 모의** |
| Drive 동기화 | 12개 하위 폴더와 페이지네이션, 중첩 경로, 새 PDF·변경 PDF·무변경 재실행 | 실제 Edge 코드 → SQL |
| Drive 경합·오류 | 동시 요청, DB 쓰기 실패 감지, webhook 커서 유지 및 재시도 | 실제 DB 실패 주입·Edge 코드 |
| PDF 열기 | PDF 바이트와 MIME, 비인증·잘못된 ID·폴더 요청 거부 | 실제 Edge 코드, **브라우저 렌더링은 제외** |
| 성적·스펙·커뮤니티·알림 | 저장·완료→스펙 분류·중복 방지·댓글/좋아요·읽음 | 실제 저장 모듈, **브라우저 전용** |

Supabase SDK/HTTP는 작은 테스트 어댑터로 대체한다. 지원하지 않는 메서드는 자동 성공시키지 않는다.
Auth는 최소 역할/사용자 fixture, Storage는 최소 메타데이터 테이블과 실제 업로드 바이트로 대체한다.
따라서 실제 로그인, JWT 갱신, PostgREST 직렬화, HTTP/CORS, signed URL 검증을 대신하지 않는다.
마이그레이션 0001 및 0003~0012는 실행한다. 호스팅 `pg_cron/pg_net`이 필요한 0002는 제외하고 `pgcrypto` 확장 설치문만 생략한다.
Deno 실행 파일이 없어 `check:edge` / `test:edge`는 실행하지 않았다. 이 시뮬레이션에서는 Edge TypeScript를 변환해 Node VM에서 실행한다.

## 이번 검사 결과

seed `20260929`, 가상 사용자 **12명**, 시나리오 **24개 모두 통과**.

- 과목 56개, 주간 수업 시간대 112개, 강의 진도 기록 56건.
- 학습 목표 92개, 계획/항목 각 80개, 실제 학습 실행 36건.
- 월간/기한 일정 24건, 반복 기타 일정 24건. 건수에는 취소·완료 이력이 포함된다.
- 노트 17개, 문제은행 과목 12개, 문제 181개.
- seed `314159`, 사용자 5명으로도 24개 모두 통과.
- 기존 검사 포함 `npm test` **75개 통과**, TypeScript 검사·변경 파일 ESLint·프로덕션 빌드 통과.
- 영구 DB를 종료 후 `simulate:inspect`로 다시 열어 데이터 보존 확인.

재현해 수정한 문제:

1. 파일 변경이 없는 Drive 동기화도 버전을 증가시키던 문제. 수동 동기화와 webhook이 같은 저장 로직을 사용하고, 동시 갱신은 버전 조건으로 재시도한다.
2. Drive DB 저장 오류가 성공처럼 처리되거나 webhook 변경 커서가 먼저 진행되던 문제. 저장 실패를 감지하고 커서를 유지한다. webhook은 기존 정책대로 오류를 기록하고 200 응답하므로 자동 재시도가 보장되지는 않으며, 다음 알림 또는 수동 동기화가 필요하다.
3. Drive 연결 해제가 GET 요청에도 실행되던 문제. POST만 허용하고 DB 조회/삭제 오류를 확인한다.
4. 자격증 완료 이력이 인코딩이 깨진 분류 비교 때문에 경험으로 저장되던 문제. 기존 공통 분류 함수를 사용한다.

## 다음 검증과 배포 순서

1. 별도 **테스트 Supabase 프로젝트**를 정하고 마이그레이션·Storage·Edge Function을 배포한다. Git 브랜치는 Supabase DB를 격리하지 않는다.
2. 테스트 계정 2개로 실제 회원가입/로그인, 계정 전환, 로그아웃, 새 브라우저 로그인 후 시간표·진도·계획 복원을 확인한다.
3. 별도 Google 테스트 계정/테스트 폴더로 동의 화면 → 폴더 선택 → 동기화 → PDF 수정 → 변경 반영 → 열기 → 해제/재연결을 확인한다. 실제 토큰이나 PDF 원본은 보고서에 기록하지 않는다.
4. 배포 도메인의 CORS/JWT/redirect URL, PDF.js worker 및 CSP를 확인한다. Edge에서 PDF 다운로드가 성공해도 브라우저 차단까지 해결되었다는 뜻은 아니다.
5. 실제 webhook 전달과 채널 갱신 cron을 확인하고, 문제은행은 작은 PDF로 실제 Gemini 응답과 비용 한도를 검증한다.
6. 성적·스펙·커뮤니티·알림까지 기기 간 보존이 필요하면 별도 스키마·RLS·저장 연동을 구현한다. 현 P0 검사만으로 서버 저장이 추가되지 않는다.
7. 검토 후 DB-ver 커밋/푸시 및 수정한 Edge Function 배포를 진행한다. **이번 작업에서는 원격 DB 변경·배포·커밋·푸시를 하지 않았다.**
