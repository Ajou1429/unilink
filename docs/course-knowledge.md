# 과목 지식 DB 기반 코칭

개정일: 2026-10-30. 사용자가 전달한 과목 지식 DB 설계를 기존 노트·Drive·학습 상태·코칭 승인 구조에 통합한다. 기존 `docs/database/coaching-harness.md`, `docs/topic-learning.md`, `docs/topic-checks.md`를 대체하지 않고 자료 이해 계층을 연결한다.

## 목적과 경계

- PDF를 매번 계획 생성 모델에 보내지 않는다. 자료 구조와 실제 수업 진도의 상세 근거를 버전별 DB에 저장한다.
- 단순 주제명이 아니라 개념·공식·예제·문제 유형·실습·선수지식·목표·요구 깊이를 코칭 입력에 전달한다.
- 강의계획서의 예정 진도, 자료 제공 범위, 실제 수업 진도, 분석 범위, 자기평가, 문제풀이 점수, 완료·실제 시간은 별도 근거다.
- 외부 검색은 실제 PDF에서 추출한 단원·개념·깊이에 대한 보조 근거다. 고급 외부 주제를 필수 수업 범위에 넣지 않는다.
- 과목 난이도 및 시간 범위는 AI 추정이다. 타 학생의 실측 평균이나 검증된 개인 최적 가중치로 표시하지 않는다.
- 일정·시험 날짜를 자동 확정하지 않는다. 기존 후보 확인 및 계획 승인 절차를 유지한다. 생성된 계획도 승인 전에는 실행 계획으로 저장하지 않는다.

## 처리 흐름

1. 계획 요청 전에 브라우저의 학습 변경 사항을 기존 P0 동기화로 저장한다.
2. 활성 목표와 그 수업/개인 학습에 명시적으로 연결된 PDF만 찾는다. 제목이 비슷한 다른 수업을 가져오지 않는다. 수업의 학기/교수별 분리는 기존 수업·목표 ID를 따른다.
3. 최초 원본 인덱스 단계는 PDF 바이트 해시와 페이지 수를 확인한다. Drive가 아직 동기화되지 않았다면 분석하지 않고 변경 반영을 요구한다.
4. 모든 PDF의 전체 페이지를 10쪽 이하 구간으로 나누어 구조 분석한다. 파일명 대신 실제 내용을 보고 혼합 문서를 구간별로 분류한다. 강의계획서 사실과 실제 자료의 단원을 구분한다.
5. 실제 수업 기록의 노트·페이지 범위 또는 유일하게 일치하는 단원/개념을 찾는다. 해당 범위 중 상세 분석이 없는 부분만 최대 6쪽씩 추가 분석한다. 모호한 경우 확인 필요로 남긴다. 업로드 시각이나 현재 날짜로 수업 진도를 추정하지 않는다.
6. 검색이 설정되고 별도 동의가 있으면 실제 단원·개념·깊이를 검색한다. 새 상세 분석에서 기존에 없던 개념이 발견된 경우에만 추가 검색 후보를 만든다.
7. PDF별 구조·상세 분석과 검색 결과를 DB에 저장한다. 원본 PDF/페이지/해시/버전, 모델·프롬프트 버전, 인용 근거, 토큰 사용량을 연결한다.
8. 코칭은 DB에서 관련 상세 내용, 제한된 과목 구조/강의계획서 근거, 검색 근거를 가져온다. 이해도 자기평가, 확인 문제 결과, 실제 학습 시간, 수업 진도, 과제·시험·기존 계획, 빈 시간을 기존 컨텍스트와 함께 사용한다.
9. 실제 자료에 맞는 개념 학습·문제·코딩·실습 등 구체 작업을 생성한다. 근거가 부족하면 임시 추천임을 밝힌다. 총 예산·시간 창·수업·휴식 검증과 사용자 승인은 그대로 적용한다.

### 세 가지 핵심 경우

| 경우 | PDF 접근/모델 분석 | 외부 검색 | DB |
| --- | --- | --- | --- |
| 최초 생성 | 연결된 모든 PDF 인덱스, 전체 페이지 구조 분석, 실제 진도 범위 상세 분석 | 설정·동의 시 실제 개념별 검색 | 단계별 결과 저장 후 코칭 조회 |
| 새 수업 진도 | 기존 상세 범위 차감 후 부족한 페이지에만 분석. 예: 3~5쪽 완료 상태에서 3~7쪽 요청 시 6~7쪽만 전송 | 기존에 없는 개념만 후보. 동일 개념은 캐시 | 기존 결과 보존 + 상세 결과 추가 |
| 동일 진도 재생성 | 원본 다운로드·PDF 모델 호출 없음 | 재검색 없음 | 지식과 최신 학습 상태 조회 후 계획 생성 |

신규/변경 PDF는 해당 파일만 처리한다. 노트 메타데이터만 바뀌면 인덱스에서 바이트를 다시 확인할 수 있지만, 같은 해시의 비싼 구조·상세 분석은 재사용한다. 자기평가·실제 학습 시간만 바뀌면 지식 키가 바뀌지 않는다. 명시적 PDF 재분석은 새 분석 세대를 만들고 이전 결과를 삭제하지 않는다. 다른 PDF와 같은 개념의 검색 근거는 유지한다.

## DB 구조 및 안전장치

`course_knowledge_tasks` 한 테이블이 작업 체크포인트와 구조화된 지식 아티팩트를 겸한다. 학습 상태 테이블을 중복 생성하지 않는다.

- `kind`: `index`, `overview`, `detail`, `research`, `refresh`(명시적 재분석 세대).
- `user_id`, `goal_id`, `note_id`: 복합 소유권 FK로 다른 계정 자료와 결합할 수 없다.
- `task_key`: 모델/프롬프트, 자료 바이트 해시, 페이지 범위, 재분석 세대에 기반한 결정적 키. 원본 인덱스는 노트 버전·수정 시각도 반영한다.
- `payload`: 구조화된 강의계획서 사실, 단원 개념·예제·실습·근거 또는 실제 검색 근거. 개별 레코드 최대 100KB.
- `status`, `attempts`, `lease_token`, `lease_until`: 중복 호출, 만료 작업 재개 및 늦은 작업의 결과 덮어쓰기 방지.
- `usage_payload`: PDF/검색 응답 토큰과 검색 도구 호출 횟수. 기존 코칭 사용량과 별도로 보존한다.
- 브라우저는 자기 결과만 읽는다. 쓰기·작업 예약·결과 공개 RPC는 service role 전용이다.
- 작업 공개와 노트 버전/수정 시각 검사는 같은 DB 트랜잭션에서 수행한다.
- 사용자당 동시에 하나의 분석 단계만 진행한다. 24시간 보수적 60단계 한도, 단계당 최대 3회 시도, 임대 150초, 외부 요청 115초 제한이다.
- 성공 결과를 보존한 채 실패 단계만 재시도한다. 3회 실패 후에는 원인을 해결한 뒤 해당 PDF 재분석으로 새 세대를 만들 수 있다. 검색만 실패하면 PDF/DB 근거의 제한 추천을 허용한다.

계획 생성까지 모든 PDF 처리를 한 HTTP 요청에 묶지 않는다. 한 요청이 한 단계를 예약하고 Edge 백그라운드 작업으로 처리하며, 화면은 상태를 조회하고 다음 단계를 이어간다. 창을 닫으면 현재 단계까지만 완료될 수 있고, 다시 열어 ‘분석 이어가기’를 누르면 저장된 체크포인트부터 재개한다. 별도 상시 워커를 배포한 것은 아니다.

작업이 실행 중인 대기 조회에서는 인덱스된 임대 상태만 확인해 `working`을 반환한다. 매 3초마다 전체 분석 JSON을 다시 읽지 않고, 단계가 끝났을 때 상세 결과와 다음 작업을 계산한다.

## 외부 검색

OpenAI Responses의 `web_search` 도구를 사용한다. 별도 검색 사업자 키는 필요 없지만 검색 지원 모델과 도구 사용 비용이 필요하다. 한 연구 단계의 검색 도구 호출은 최대 2회로 제한한다.

- 검색 입력은 추출된 단원/개념/요구 깊이이다. 원본 PDF 전체, 사용자 이해도·학습 이력, 계정 정보는 검색 입력에 포함하지 않는다. 개념 자체가 비공개 정보일 수 있어 별도 동의를 받는다.
- 실제 완료된 검색 도구 호출이 있어야 성공으로 처리한다. 응답의 실제 검색 출처/인용 URL에 없는 주소는 검증에서 거절한다.
- URL, 제목, 확인 일자, 관련성, 신뢰도 설명, 근거, 불확실성, 난이도별 추정치와 시간 추정 근거를 저장한다. 화면에 클릭 가능한 출처를 표시한다.
- API 미설정·미지원·실패·검색 동의 거절을 검색 완료로 가장하지 않는다. `disabled`, `unavailable`, `pending`, `failed` 상태를 구분한다.
- 출처가 실제 검색되었다는 검증이 내용의 학술적 정확성까지 보장하지는 않는다. 시간·수준·난이도는 보조 추정이며 과목 원본 근거가 우선이다.

API 근거: [OpenAI Web Search](https://developers.openai.com/api/docs/guides/tools-web-search), [PDF Inputs](https://developers.openai.com/api/docs/guides/file-inputs). PDF 입력은 페이지 이미지도 처리하므로 이후 계획 요청에서 원본 대신 구조화된 DB 근거를 사용하는 것이 핵심이다.

## 적용 순서

운영 대상은 `lqwpcwzjbqeunqfliaso`이다. 2026-10-30에 기존 0024 다음으로 0025·0026·0027을 적용하고 관련 함수를 배포했다. 배포 때마다 대상 ref를 확인하며 예전 프로젝트 `beqdvsfwybuisylxbqko`에는 이번 변경을 적용하지 않는다.

1. 대상 DB의 기존 마이그레이션 상태 확인 후 `0026_course_knowledge.sql`, `0027_coaching_service_settings.sql` 적용. 0025 미적용 환경은 먼저 적용한다.
2. `course-knowledge`, 변경된 `coaching-propose`, 공통 PDF 읽기를 사용하는 `note-analyze` Edge Functions 배포.
3. API 키는 기존 Supabase 서버 비밀값에만 유지한다. 비밀정보가 아닌 활성화 상태는 서버 전용 `coaching_service_settings`에서 관리할 수 있다. 다음 환경변수를 명시적으로 지정하면 DB 설정보다 우선한다:

```text
COURSE_KNOWLEDGE_ENABLED=true
COURSE_KNOWLEDGE_MODEL=<PDF 입력과 구조화 출력을 지원하는 모델>
OPENAI_API_KEY=<기존 서버 전용 키>
COURSE_RESEARCH_ENABLED=false
# 검색 검증을 마친 뒤에만 true로 전환
COURSE_RESEARCH_MODEL=<web_search와 구조화 출력을 지원하는 모델>
```

분석 모델은 미설정 시 기존 `NOTE_ANALYSIS_MODEL`, 이후 `COACHING_MODEL`을 사용한다. 임의로 모델을 교체하지 않는다. 검색은 `COURSE_RESEARCH_ENABLED=true` 및 명시적 `COURSE_RESEARCH_MODEL`이 있을 때만 가능하다. 기존 코칭 활성화 설정도 필요하다.

환경변수가 없을 때는 DB의 `knowledge_enabled`, `research_enabled`, `topic_check_enabled`, `analysis_model`, `research_model`을 사용한다. 이 테이블은 브라우저·anon·authenticated의 조회/쓰기를 모두 차단하고 service role 및 운영 DB 관리자만 관리한다. API 키·액세스 토큰은 저장하지 않는다. 실제 운영 코칭 이력에서 확인한 모델은 `gpt-4.1-mini`이며 기존 모델·키를 유지한다. 과거 문서의 `gpt-6.1-sol` 선택안이 현재 운영 설정이라는 의미는 아니다.

4. 프런트 빌드 환경에 `NEXT_PUBLIC_COURSE_KNOWLEDGE_ENABLED=true` 설정. GitHub Pages 워크플로는 동명의 Repository Variable을 읽는다. API 키는 절대 `NEXT_PUBLIC_*`에 넣지 않는다.
5. 소량의 테스트 PDF, 기록된 진도, 반복 추천, 외부 검색 지원/출처를 실제 계정으로 검증한 뒤 공개 사용량을 확대한다.

서버·프런트 플래그는 초기에는 꺼져 있어 기존 운영 기능을 갑자기 막지 않는다. 서버만 켜면 구형 프런트의 미분석 계획 요청은 409로 거절될 수 있으므로 함께 배포한다. 롤백은 두 플래그를 끄는 방식이며 새 DB 결과를 삭제할 필요가 없다.

## 현재 제한과 다음 단계

- PDF별 기존 20MB/50쪽 제한, 목표별 조회 노트 40개·수업 기록 100개·지식 아티팩트 1500개 상한을 유지한다. 초과 시 조용히 일부만 처리하지 않고 범위 조정을 요구한다.
- 개별 노트의 기존 수동 요약은 새 분류/페이지별 지식 스키마를 충족하지 않는다. 기존 수동 후보와 학습 기록은 보존하며, 필요한 새 구조 정보만 별도 분석한다. 텍스트 OCR의 직접 인용 진위는 독립 재검증하지 않으므로 AI 추출 근거로 취급한다.
- 모호한 주제/페이지 연결은 자동 추정하지 않는다. 수업 기록에 노트 제목과 실제 페이지 범위를 입력하면 상세 분석이 가능하다.
- 현재 코칭 입력은 최신 수업 진도 중심의 상세 근거와 일부 과목 구조를 제한 길이로 선별한다. 모든 과목의 모든 PDF를 무조건 보내지 않으며 잘린 범위는 표시한다. 임베딩 기반 의미 검색, 대규모 자료 전용 워커는 다음 확장 대상이다.
- 강의계획서의 주차별 교육과정은 학기 참고 로드맵으로 조회된다. 실행 계획 API의 1~14일 계약과 승인을 유지하며, 학기 전체를 자동 달력 배치하는 새 스케줄러까지 구현했다고 주장하지 않는다.
- 새 자료 분석은 기존 `goal_topics`/날짜를 자동 확정하지 않는다. 기존 수동 후보 확인·주제 기록·확인 문제 흐름을 유지한다. 새 지식 단원에서 바로 주제 확인 문제를 만드는 통합은 별도 확장이다.
- 시간 보정은 현재 모델이 근거 범위·학습 이력·자기평가·검증 결과를 해석하도록 연결한 단계다. 학습된 개인 가중치나 통계적 시간 예측 모델은 아직 아니다.
- 다음에는 계획 항목과 지식 단원 간 고정 식별자 연결, 주제별 이해도 평가 근거 확대, 실제 소요 시간/미완료 이유 수집, 반복 자료의 OCR/텍스트 우선 처리, 평가셋을 통한 추천 품질 측정을 진행한다.
- 충분한 실행 데이터가 쌓이면 개념/실습/복습별 기준 시간과 개인 조정 요인을 보정한다. 표본 수·불확실성·추천 버전·실제 성과를 함께 기록하고 기존 추천과 비교한다. 이 단계가 UniLink 데이터 기반 개인화의 다음 축이다.

## 검증 범위

테스트는 단순 문서상의 설계가 아니라 실제 작업 선택 함수, 실제 PostgreSQL 스키마/RLS/RPC 및 실제 Edge 처리 코드를 실행한다. OpenAI·Drive 네트워크는 모의 응답을 사용하며 실제 결제 모델의 교육적 품질을 입증하는 테스트는 아니다.

- 최초 전체 자료 분석, 같은 상태 재요청 0회, 신규 진도 누락 페이지만 분석, 범위 확장 차집합, 새/수정 PDF만 갱신, 동일 해시 재사용.
- 학습 시간·이해도 변화와 지식 캐시 분리, 진도 상태 분리, 모호한 매핑 경고, 실패 결과 보존.
- 실제 검색에서 확인되지 않은 URL·잘못된 페이지·근거 없는 추출 거절.
- 사용자 격리, 서비스 전용 쓰기, 중복 예약 차단, 만료 임대 재개, 늦은 작업 차단, 원본 변경 시 공개 거절.
- 실제 PDF 페이지를 잘라 모의 모델로 전송하고 결과를 DB에 저장한 뒤, 최종 `coaching-propose` 모델 입력에 상세 개념이 전달되는 통합 흐름.
- 데스크톱/모바일 UI의 동의, 진행 상태, 출처 링크, 반복 추천 재사용 및 가로 넘침 점검.
