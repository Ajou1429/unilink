## 1. 결론

추천의 큰 구조를 다시 만들 필요가 있다는 결론은 아니다. 다만 **기록을 저장·취소·조회하는 과정과 일정을 승인·변경하는 과정에 실제 결함이 있다.** 이 상태에서는 LLM이 올바르게 판단해도 잘못된 학습 이력을 입력받거나, 정상 계획이 서버에서 실패하거나, 나중에 일정이 충돌할 수 있다.

이번에 확인한 사항은 16개다. P1 4개는 다음 기능 확장보다 먼저 수정할 대상으로, P2 11개는 같은 안정화 작업에서 수정할 대상으로, P3 1개는 표시 오류로 분류한다. 운영 사용자에게 이미 발생했다는 의미는 아니다. 발생 가능한 조건을 합성 데이터로 재현하거나 서로 다른 입력 계약을 대조해 확인했다.

**이번 작업은 점검과 재현 테스트·문서 작성이다. 서비스 코드 수정, 운영 DB 조회·변경, 유료 모델 호출, 커밋·푸시·배포는 수행하지 않았다.**

## 4. 우선 수정할 P1

### F01. 파일 처리 중 계정을 바꾸면 다른 계정에 저장된다

**발생 조건:** A 계정에서 파일을 올리고, 내용 추출 또는 AI 분류가 끝나기 전에 B 계정으로 바꾼다.

`run()`은 시작 계정을 보존하지 않고 비동기 분류 후 `attachNote()`를 실행한다. 노트 저장 함수는 그때 로그인한 사용자를 다시 읽는다. 따라서 B 계정의 정상 권한으로 A의 파일을 저장할 수 있다. 화면이 계정 변경 시 다시 만들어져도 이미 실행 중인 비동기 함수는 취소되지 않는다. 처리 로그도 완료 시점 계정의 저장소에 남는다.

- 재현 R16: A의 파일이 B의 `notes` 행과 B의 파일 경로에 저장되고 B의 처리 로그에 표시됐다.
- 위치: [pipeline.ts:198](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/file-intake/pipeline.ts#L198), [pipeline.ts:207](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/file-intake/pipeline.ts#L207), [my-notes-storage.ts:381](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/my-notes-storage.ts#L381).
- 수정 방향: 작업 시작 시 사용자와 화면 작업 세대를 고정하고, 모든 저장·재전송 직전에 동일한지 확인한다. 계정 변경 시 대기열과 진행 중 작업을 중단한다. 새 계정에서 이전 작업을 계속하지 않는다.
- 영향 범위: 파일 분류·노트·강의계획서·문제은행·Drive 업로드·처리 로그. 새 추천 알고리즘은 필요 없다.

### F02. 예전 카드의 취소가 새 이해도까지 없앤다

**발생 조건:** 같은 주제를 여러 번 기록하고 이전 카드에서 취소한다.

처음 만든 주제의 카드는 취소하면 주제를 무조건 `archived`로 바꾼다. 그 사이 쌓인 새 이해도나 노트 연결을 검사하지 않는다. 기존 주제 카드도 저장 직전 상태를 새 관측으로 다시 넣으므로 이후의 정상 기록을 덮어쓴다. 회차·문항 취소도 현재 값의 변경 여부를 비교하지 않는 같은 형태다.

- R08: 어려움 2/5로 새 주제 생성 → 이해함 5/5 추가 → 첫 카드 취소 → 주제 전체가 숨겨지고 최신 5/5가 코칭에서 빠졌다.
- R10: 기존 5/5 → 첫 카드 2/5 → 다음 카드 4/5 → 첫 카드 취소 → 최신 4/5가 5/5로 바뀌었다.
- 위치: [apply.ts:217](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/chat-record/apply.ts#L217), [apply.ts:222](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/chat-record/apply.ts#L222).
- 수정 방향: 카드가 만든 관측 ID를 보존하고 그 관측만 취소한다. 최신 관측 ID가 달라졌다면 예전 상태로 덮어쓰지 않는다. 생성 주제도 다른 정상 기록이 있으면 숨기지 않는다. 서버에서 한 번에 검사·적용해야 한다.
- DB: 관측의 취소·수정 관계를 표현할 필드 또는 별도 이력과, 그 기록을 반영하는 현재 상태 조회가 필요하다. 이력을 전부 삭제하거나 최종 값을 추측해 복구하면 안 된다.

### F03. 빠르게 보낸 두 메시지가 상태를 꼬이게 한다

한 메시지 안의 여러 기록은 순서대로 저장하지만, **서로 다른 메시지 사이에는 대기열이 없다.** 각 요청이 별도로 읽은 주제 목록으로 새 주제를 만들고, 관측 시각도 사용자가 말한 시각이 아니라 저장 시각을 쓴다.

- R12: 나중 메시지 ‘이제 이해함 5/5’가 먼저 처리되고, 먼저 보낸 ‘모름 1/5’ 응답이 늦게 도착하면 최종 상태가 1/5가 됐다.
- R15: 두 요청이 같은 새 주제가 없다고 읽으면 동일한 이름의 주제 두 개가 생성되고, 하나는 1/5·다른 하나는 5/5인 현재 상태가 함께 존재했다.
- 위치: [ChatHome.tsx:61](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/components/home/ChatHome.tsx#L61), [ChatHome.tsx:147](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/components/home/ChatHome.tsx#L147), [apply.ts:137](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/chat-record/apply.ts#L137), [apply.ts:150](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/chat-record/apply.ts#L150).
- 수정 방향: 메시지별 고정 요청 ID·입력 시각·순서를 갖고 저장을 직렬화한다. 같은 목표의 주제 확인과 생성·관측 저장을 서버에서 원자적으로 처리한다. 재시도도 같은 요청 ID를 사용한다. 이름만 같다는 이유로 서로 다른 계층의 주제까지 무조건 합치지는 않는다.
- 기대 효과: 하나의 사실이 여러 학습 신호로 부풀거나 과거 상태가 최신으로 둔갑하는 것을 방지한다.

### F04. 승인 전에 아직 서버로 보내지 않은 일정 변경이 빠진다

DB 승인 함수의 revision 검사는 **DB에 반영된 변경**을 기준으로 정상 작동한다. 하지만 화면의 `approve()`는 `flushP0Changes()`를 호출하지 않는다. 브라우저에는 350ms 대기열이나 실패 후 재전송 대기 변경이 있을 수 있다.

- R11: 새 09:00 일정은 로컬 대기열에만 존재 → 기존 revision으로 AI 09:00 계획 승인 성공 → 대기열 동기화 → 같은 시간에 일정과 AI 계획이 모두 저장됐다.
- 위치: [CoachingRequestPanel.tsx:279](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/components/coaching/CoachingRequestPanel.tsx#L279), [p0-sync.ts:506](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/p0-sync.ts#L506).
- 수정 방향: 승인 전에 동기화 완료를 기다리고 실패하면 승인하지 않는다. 진행 중인 이해도 저장도 기다리거나 승인을 비활성화한다. 변경 후에는 기존 revision 검사가 재생성을 요구하게 한다.
- 한계: 다른 기기가 승인 뒤 새 일정을 추가하는 경우까지 절대 금지한다는 의미는 아니다. 이번 문제는 승인 시 이미 알고 있는 미전송 변경이 빠지는 것이다.

## 5. Learner State·개인화 입력 문제

### F05. 삭제한 수업 진도가 다시 추천 근거로 들어간다

회차 삭제는 DB 행을 지우지 않고 `metadata.deleted=true`를 남긴다. 그러나 코칭과 과목 지식 조회는 이 표시를 제외하지 않는다. 최근 10회차 한도도 삭제 행이 먼저 차지할 수 있다.

- R03: 삭제 표시된 ‘Deleted advanced topic’이 `recent_course_progress`와 과목 지식의 `actual_class_progress` 모두에 남았다.
- 위치: [p0-sync.ts:400](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/src/lib/p0-sync.ts#L400), [context.ts:102](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/supabase/functions/_shared/coaching/context.ts#L102), [courseKnowledgeStore.ts:24](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/supabase/functions/_shared/courseKnowledgeStore.ts#L24).
- 수정: 삭제 행을 **조회 한도 적용 전에** 제외한다. 회차 선택 화면도 같은 활성 기준을 사용한다. 삭제 취소와 과거 감사용 보존은 구분한다.

### F06. 취소한 이해도를 개인화의 과거 변화로 읽는다

취소가 이전 상태를 새 관측으로 추가할 뿐 잘못된 관측을 무효화하지 않는다. `loadUnderstandingHistory()`는 최근 관측을 그대로 읽으므로 오입력이 이후에도 사용된다.

### F07. 대화 원문의 일부가 저장되고 다음 추천에도 전달된다

## 6. 추천 시간·일정 변경 문제

### F10. 과거 학기의 수업이 계속 현재 시간표를 막는다

### F11. 정상 계획을 시간 보정기가 실패 처리한다

최종 검증기는 설정된 연속 학습 상한을 초과할 때 휴식을 요구한다. 보정기는 짧은 항목 사이에도 무조건 휴식 간격을 강제한다. 또 완료 기준이 있는 한 덩어리 작업을 이른 짧은 창에 먼저 쪼갠 뒤, 쪼개졌다는 이유로 실패시키며 나중의 충분한 창을 먼저 시도하지 않는다.

- R01: 09~10시 60분 가용, 연속 상한 90분. 09:00 30분 + 09:30 30분은 최종 검증을 통과하지만 보정기는 502로 실패했다.
- R02: 09:00~09:30과 10:00~11:00이 열려 있을 때 완료 기준이 있는 60분 작업을 10시에 그대로 넣을 수 있는데도 실패했다.
- 위치: [contract.ts:236](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/supabase/functions/_shared/coaching/contract.ts#L236), [contract.ts:249](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/supabase/functions/_shared/coaching/contract.ts#L249), [contract.ts:323](https://github.com/Ajou1429/unilink/blob/7ba30a643da3dccbf0ae58491c0b58eb6fdebb64/supabase/functions/_shared/coaching/contract.ts#L323).
- 수정: 이미 유효한 계획은 보존한다. 보정기와 검증기가 같은 휴식·전환 규칙을 사용하게 하고, 구조화 완료 기준이 있는 작업은 통째로 들어가는 창을 먼저 찾는다. 무조건 잘게 나누거나 상한을 없애지 않는다.
- 비용 영향: 현재 서버는 실패 시 최대 한 번 더 생성한다. 정상 결과를 보정 과정에서 거절하면 필요 없는 호출·지연이 생길 수 있다. 이번 점검에서는 유료 재호출을 실행하지 않았다.

## 8. 확인된 정상 보호와 오탐 배제

다음 구조는 이번 검토에서 유지할 근거가 있었다. 위 결함이 있다고 모든 보호가 무효라는 뜻은 아니다.

- 서버의 사용자별 조회와 DB 소유자 권한, 선택한 목표·확정 주제·허용 방법 ID 검증.
- 자기평가와 채점 결과를 별도 입력으로 보내는 기본 구조.
- `coaching-propose`의 일회성 요청 원문 비저장 및 과거 자유 피드백을 영구 성향으로 사용하지 않는 정책. 단, F07의 새 채팅 인용 경로는 별도 보완해야 한다.
- PDF 버전·내용 해시·모델·지침별 분석 캐시, 검색 출처 확인, 오래된 확인 문제 표시와 무효 처리.
- 수동 계획의 출처 확인·중복 보호와 기존 예약 시간 차단.
- 가용 창·하루 분량·목표 제한·시험 대비 종료 시점 등을 검증하는 기본 코드. 단, F10·F11·F13은 그 주변 경로의 일관성 문제다.
- DB에 커밋된 변경에 대한 revision 검사, 만료된 제안 차단, 동일 제안 중복 승인 방지의 기존 자동 검증.
- `in_progress` 계획 항목이 코칭에서 빠진다는 의심은 **버그에서 제외**했다. 실제 DB는 해당 상태를 허용하지 않는다. 화면 일부에 그 문자열이 있어도 DB에 존재하는 진행 항목이 누락된다고 보고하면 오탐이다(C01).

## 9. 버그와 구분해야 하는 미완성·평가 과제

1. **계획 완료 버튼만으로 실행 기반 개인화가 완성되지 않는다.** 현재 AI 계획 체크는 주로 `study_plan_items.status`를 바꾼다. 실제 시간·수행 범위·부분 완료·미완료 사유·완료 기준 달성을 `study_sessions`에 연결하는 화면 작업은 남아 있다. 코칭이 이 데이터를 읽는 코드가 있어도 사용자가 실제로 기록할 경로가 충분하지 않으면 개인화 근거가 쌓이지 않는다.
2. **새 문제은행 본문 분석과 코칭 본문 활용은 다른 단계다.** 최신 메인에는 문항 본문·그림 저장이 있지만 코칭은 여전히 활동 단계 위주로 읽는다. F16의 출처 누락을 먼저 고치고, 본문·주제 연결·필요 구간 검색은 별도 고도화로 진행한다.
3. **과목 지식 분석과 확인 문제의 주제 등록 경로는 아직 분리되어 있다.** 확인 문제는 기존 `note_analysis_candidates`에서 확정한 주제를 요구한다. 자동 과목 지식 분석을 끝내거나 채팅으로 새 주제를 만들었다고 곧바로 모든 주제의 확인 문제가 만들어지는 것은 아니다.
4. **검색 결과의 사실 적합성과 추천의 구체성은 별도 품질 평가가 필요하다.** 검색을 실제 호출하고 URL을 확인하는 것만으로 그 자료가 해당 수업·시험에 맞는지는 증명되지 않는다. 일반 검색 추정과 강의 PDF 사실, 개인 이해도는 계속 분리해야 한다.
5. **일별 선택 작업·자유 텍스트의 의미는 주로 LLM 지침에 의존한다.** 시간·소유권 검증과 달리 ‘고른 과제만 다뤘는가’, ‘새로 만든 연습을 실제 기출이라고 말했는가’ 같은 의미 검사는 제한적이다. 대표 사례의 결과 검증과 출처 연결을 보강한다.
6. **성능 향상률은 측정하지 않았다.** 이번에는 유료 LLM을 새로 호출하지 않았다. 상태 오류 수정이 근거의 정확성을 높이는 조치라는 것과, 실제 추천 품질이 몇 % 좋아졌는지는 구분한다.
7. **운영 적용 여부는 미검증이다.** 메인에 함수·마이그레이션이 있다고 운영에 적용된 것으로 표시하지 않는다. 운영 서버 버전·마이그레이션·기능 설정을 별도로 확인한다.
8. **오래된 검색 캐시·누적 분석 이력 한도도 후속 점검한다.** 자료 기반 검색의 주기적 갱신과 누적 작업 1,500개 한도에 대한 보관 정책은 장기 운영 과제다. 이번에 실제 운영 장애로 확인한 항목은 아니다.

## 10. 수정 순서와 하네스 반영

### 1순위: 사용자·관측 경계 보호

F01~F03을 먼저 처리한다. 계정별 작업 소유권, 메시지 요청 ID·시각, 주제 생성, 관측 취소·수정을 하나의 정합성 기준으로 묶는다. F06·F07·F09·F12도 이 단계의 유효 관측 기준에 연결한다. 기존 수동 입력과 노트에서 등록한 주제를 손상시키지 않아야 한다.

**완료 조건:** 계정 전환·응답 역전·같은 주제 동시 입력·이전 카드 취소·중복 재시도·새 채팅 후 늦은 응답을 시험해 다른 사용자/후속 기록을 바꾸지 않는다. 취소 기록은 감사용으로 남겨도 추천 근거에서는 제외한다.

### 2순위: 현재 일정과 변경 경계 일치

F04·F05·F10·F11·F13을 처리한다. 생성 전뿐 아니라 승인 전과 미루기/변경 후에도 같은 일정·유효 기록 기준을 사용한다. 전체 추천 전략이나 새로운 우선순위 공식을 바꾸는 작업이 아니다.

**완료 조건:** 정상 30+30 계획은 보존되고, 과거 학기·삭제 회차는 현재 일정/진도에서 빠지며, 미전송 변경·충돌·시험 이후 배치는 그대로 승인되지 않는다.

### 3순위: 근거의 의미와 출처 보존

F08·F14·F16을 처리한다. 채팅·화면·DB·LLM 입력의 척도를 통일하고, 파일·시험 구분과 문항 활동 기록을 유지한다. F15는 이 작업과 함께 고칠 수 있다.

**완료 조건:** 중간/기말의 같은 번호를 구분하고, 읽기·해설 이해·독립 풀이를 혼동하지 않는다. 분류 수정 후에도 보존해야 할 단계가 남는다.

### 4순위: 실제 과목 대조 평가와 운영 확인

운영 버전과 DB 변경 범위를 확인한 뒤, 실제 과목 2개·개인 목표 1개에서 같은 PDF와 일정은 고정하고 이해도·남은 시간·마감만 각각 바꾼다. 입력된 근거, 추천 분량·수준·완료 기준, 수정 부담, 호출 수·비용·지연을 비교한다. 합성 DB 시험만으로 실제 모델 품질 평가를 대신하지 않는다.

### 5순위: 미완성 실행 기록·승인형 재계획·개인 보정

기존 로드맵을 유지한다. 실제 공부 결과를 저장하는 화면 → 변경 계획 미리보기와 승인 → 반복된 개인 기록을 근거로 시간·분량 보정 순서다. 자동 파인튜닝이나 한 번의 요청을 영구 성향으로 만드는 방식은 도입하지 않는다.

### 공통 하네스 기준

- 단일 오케스트레이터 구조를 유지한다.
- 입력 수집 단계: 같은 사용자·유효 관측·현재 일정·자료 출처·척도를 보장한다.
- 생성 단계: 현재 요청과 과거 관측을 분리하고 부족한 근거를 숨기지 않는다.
- 검증 단계: 같은 배치 규칙으로 판정하고 유효한 결과를 보정기가 깨뜨리지 않는다.
- 승인·변경 단계: 미전송 변경·최신 상태·충돌·재시도를 확인한다.
- 기록 단계: 수정/취소와 실제 학습 결과를 구분하고, 과거에 무슨 일이 있었는지 추적 가능하게 한다.
- 평가 단계: 이번 재현 사례를 정상 동작 기대값으로 바꾼 회귀 시험과 실제 추천 대조 평가를 함께 사용한다.

## 11. 운영 데이터에 대한 주의

이번 결과는 운영 개인 데이터가 이미 오염됐다는 진단이 아니다. 운영 데이터는 읽거나 수정하지 않았다. 수정 후 필요한 데이터 점검도 사용자별·소스별로 범위를 정하고 다음 원칙을 따른다.

1. 같은 이름의 주제를 자동으로 전부 합치지 않는다. 실제로 다른 단원일 수 있다.
2. 이해도 이력을 전부 지우거나 최신 점수를 추측해서 복구하지 않는다.
3. 취소·오입력·정상 학습 변화가 구분되는 경우에만 표시를 보완한다.
4. 과거 학기 수업을 삭제해 해결하지 않는다. 현재 시간 차단에서만 제외하고 이력은 보존한다.
5. 문제 원본·학습 단계·노트 연결·코칭 승인 기록을 보존하는 마이그레이션과 되돌리기 방안을 먼저 검토한다.

현재 상태: **결함 확인과 수정 준비 완료 / 서비스 수정 미실시 / 운영 적용 미실시**.
